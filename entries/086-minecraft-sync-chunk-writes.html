A survival server that crashed mid-save lost a chunk of terrain, not just progress

After an unclean shutdown (host got killed by an OOM condition elsewhere on the box, not the Minecraft process itself) a survival world came back up with a small patch of terrain reverted to void — not just "missing the last few minutes," but an actually corrupted region file that had to be regenerated. The server had been running with default settings, which turned out to matter.

Why: region-file writes are async by default, for throughput

Minecraft's world save writes go through the OS page cache before hitting disk, and by default the server doesn't force a sync after every chunk write — it batches and lets the OS flush on its own schedule, which is faster and easier on disk I/O. That's fine as long as the process and the underlying disk both stay up. If the machine dies mid-write, whatever hadn't been flushed yet is gone, and a region file caught in the middle of a write can end up truncated or with a bad header instead of just "slightly stale." 

# server.properties
# default is false: writes are buffered, better TPS, but an
# unclean shutdown can lose or corrupt whatever wasn't flushed yet
sync-chunk-writes=true

Setting it to true forces an explicit sync on every chunk write, so the world file on disk is never more than one chunk-write behind reality — at the cost of extra disk I/O on every save, which shows up as a small but real TPS hit on spinning disks or already-loaded storage, less noticeable on NVMe.

The actual lesson

This is a durability/throughput tradeoff, not a bug fix — leave it off for a survival world on reliable hardware where a bit of lost progress on a rare crash is acceptable, but turn it on for anything running on flaky hosting, inside a VM that might get killed abruptly, or where the world data itself (not just player progress) has to survive an unclean shutdown intact.
