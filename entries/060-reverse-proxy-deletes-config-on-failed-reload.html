A working HTTPS host went dark right after a small, unrelated-looking edit in the admin UI

A self-hosted reverse proxy managing a handful of HTTPS hosts had one host edited in its web UI — nothing dramatic, just adding a custom location block. The save appeared to succeed, the UI kept showing the correct settings afterward, but the site immediately started failing TLS handshakes entirely (ERR_SSL_UNRECOGNIZED_NAME_ALERT), as if the certificate for that hostname had vanished.

Why: the underlying web server config file was gone, not just wrong

The proxy's own generated nginx config directory had no file at all for that host anymore. Its database record was still intact and correct — the UI reads from the database, which is why it kept looking fine — but the actual on-disk config nginx uses to route that hostname had been deleted. Tracing through the proxy's own save logic: on every edit it deletes the old config file, generates a new one, and tests it. If the new file fails nginx's own syntax check for any reason, the code deletes the file it just wrote instead of restoring the previous, known-working one — it only logs the failure to an internal field that never surfaces anywhere in the UI. A save that silently fails this way leaves the host with no config file at all, not the old one and not the new one. 

# recovery: hand-write the config file from the still-correct DB record
sqlite3 database.sqlite "select * from proxy_host where id = N;"
# rebuild the nginx server block from that data, copy it into
# the container's config directory, then validate before reloading
docker exec proxy-app nginx -t
docker exec proxy-app nginx -s reload

The actual lesson

Don't trust a config-management UI's own "saved successfully" state as proof the underlying service config is actually valid — if a save can ever fail an internal validation step, check whether the tool restores the previous file on failure or just deletes it. When a previously-working host breaks right after an edit with no obvious cause, compare the database's stored config against what's actually on disk before assuming the problem is anywhere else.
