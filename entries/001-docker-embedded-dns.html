Docker's embedded DNS beats hardcoded container IPs

I run a few services on a shared Docker bridge network (a proxy container, a game server panel, a couple of backend containers it talks to). At one point I wired one container's config to reach another by its bridge-network IP address, something like 172.18.0.2:25566, copied straight out of docker inspect.

That worked fine until I restarted the stack. After the restart, Docker handed out IPs in a different order — the address that used to belong to container A now belonged to container B. Everything that pointed at the old IP started connecting to the wrong service, and the symptom looked exactly like a networking outage ("connection refused" / "no route to host") rather than a stale config problem, which cost more debugging time than it should have.

The fix

Docker's embedded DNS resolves container names (or hostnames/aliases you set in Compose) on the same user-defined network automatically, and that mapping stays correct across restarts even if the underlying IP changes: 

servers:
  backend: "container-name:25566"   # good — survives restarts
  # backend: "172.18.0.2:25566"     # bad — IP can get reassigned

Bridge-network container IPs are only stable for the lifetime of the container, not the lifetime of the network. If two configs need to reference each other across a restart boundary, use the container name (or a Compose service alias), never the IP, even for "it's just internal, it won't change" cases.
