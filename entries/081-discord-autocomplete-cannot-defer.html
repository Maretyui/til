A slow autocomplete lookup made the dropdown just... not show up

A slash command option had autocomplete wired up to search a small local list — nothing that should take more than a few milliseconds. Under any real load, though, the suggestion dropdown in Discord would occasionally just stay empty, with no error anywhere in the bot's logs. The handler ran fine and returned a response; Discord's client simply never showed it.

Why: autocomplete is its own interaction type, and it has no defer

Every other interaction (a slash command, a button click, a select menu) can call deferReply() to buy extra time and edit the response in later. Autocomplete requests (InteractionType.ApplicationCommandAutocomplete) don't support that at all — there is no deferred-autocomplete response type in the API. The only valid reply is a single APPLICATION_COMMAND_AUTOCOMPLETE_RESULT callback, and it has to land inside the same roughly 3-second window every interaction gets, with no extension available. 

// This works for a slash command:
await interaction.deferReply();
const result = await slowLookup();
await interaction.editReply(result);

// This does NOT exist for autocomplete — there's nothing to defer to.
// If slowLookup() takes too long, the response is just dropped client-side.
async function handleAutocomplete(interaction) {
  const choices = await slowLookup(interaction.options.getFocused());
  await interaction.respond(choices.slice(0, 25));
}

Discord doesn't send back an error when this happens either — the client just silently shows no suggestions, which is exactly why it looked like nothing was wrong on the bot's side.

The actual lesson

Any data source backing an autocomplete handler needs to already be fast enough to answer inside the interaction's own timeout — in-memory lookups, a cached list, or a pre-warmed index, never a cold network/database call made for the first time on that keystroke. If a real query is unavoidable, cache its result and serve stale data on the next keystroke rather than trying to fetch fresh data every time, since a slow round trip has no fallback here.
