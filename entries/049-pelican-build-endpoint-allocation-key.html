A memory/CPU-only limit change threw an unrelated-looking 500

Bumping a Minecraft server's memory limit through Pelican Panel's Application API — a plain PATCH to the server's build endpoint with just memory/cpu/disk in the body — failed with a generic 500 and, once debug logging was on, an uncaught Undefined array key "allocation". Nothing about resource limits should care about network allocation at all.

Why: the endpoint expects the full build payload every time

The build-update endpoint isn't a set of independent partial-update fields — it reads allocation unconditionally while assembling the update, even when the request is only trying to change limits. Omit it and the handler throws before it ever gets to the fields that were actually being changed. 

// fails: Undefined array key "allocation"
PATCH /api/application/servers/42/build
{ "memory": 4096, "cpu": 200, "disk": 20000 }

// works: always include the server's *current* allocation id,
// even when only limits are changing
PATCH /api/application/servers/42/build
{ "memory": 4096, "cpu": 200, "disk": 20000, "allocation": 17 }

The actual lesson

An API endpoint's name and the fields you're actually trying to change don't guarantee it treats the rest of its schema as optional — some "update" endpoints are really "replace with this full document" endpoints wearing a PATCH verb. When a field-scoped edit throws on a completely unrelated key, try resending the current value of that key alongside the real change before assuming it's a deeper bug.
