A mail client on the home network couldn't connect to the mail server, by hostname

A self-hosted mail server sits on the LAN and is also reachable from the internet through a port forward on the router, using its own public domain name. Connecting from outside worked fine. Connecting from a phone on the same home WiFi, using that exact same domain name, just hung until it timed out — even though connecting to the server's raw LAN IP instead worked immediately, from the same phone, on the same network.

Why: consumer routers often don't support NAT loopback/hairpinning

The domain resolves publicly to the router's WAN IP. An internal client asking for that same public IP sends the request out toward the router's external interface — but the client itself is already behind that router, on the internal network. Hairpin NAT is the feature that lets a router notice "this traffic is destined for my own public IP and forwarded port, redirect it back inside to the LAN host" instead of just dropping it or routing it out to the internet and back. Plenty of consumer routers, including this one, simply don't implement it. 

# from outside the LAN:      client -> WAN IP:port -> router forwards -> LAN host   (works)
# from inside the LAN, by IP: client -> LAN IP:port directly                        (works)
# from inside the LAN, by domain -> resolves to WAN IP -> router has no loopback path -> hangs

The real fix vs. the workarounds

The workarounds — a per-device /etc/hosts override pointing the domain at the LAN IP, or just switching to mobile data to avoid the home network entirely — only patch one device at a time and need to be reapplied on every new client. The actual fix is a local DNS resolver on the LAN (a Pi-hole instance, in this case) with an override that answers the public domain with the internal LAN IP for anyone using it as their DNS server, so every device gets the short path automatically without needing the router to support hairpinning at all.

The actual lesson

If a service works perfectly from outside and by raw IP from inside, but hangs specifically when an internal client uses the public hostname, suspect the router's NAT implementation before digging into the service's own config — it's a routing gap, not an application bug, and no amount of retrying the connection will fix it.
