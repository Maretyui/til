Redis EXPIRE applies to the whole key, not individual hash fields

A small allowlist stored as a Redis hash — one field per trusted forwarding host, read live by a multimap module elsewhere — seemed like a natural place to also auto-expire temporary entries added for a one-off test, by calling EXPIRE on the hash key right after HSETing the new field. The expectation was that only that field would disappear after the TTL.

What actually happens

EXPIRE keyname 3600 sets a TTL on the entire key, not on whichever field was just written. Since a Redis hash is one key holding many fields, expiring it deletes every field in the hash once the TTL elapses — including long-lived entries that were never meant to expire at all. 

HSET allowlist 172.22.1.5/32 "test-entry"
EXPIRE allowlist 3600
# one hour later: the ENTIRE allowlist key is gone,
# not just the 172.22.1.5/32 field

This is easy to miss because the command reads as if it's scoped to the most recent write, but EXPIRE has no concept of "the field I just touched" — it only ever operates on the key as a whole.

The actual lesson

Redis added true per-field TTLs (HEXPIRE, HPEXPIRE, HPERSIST) in Redis 7.4 — worth checking the running version before assuming they're available. On anything older, a hash is an all-or-nothing TTL unit: either don't mix permanent and temporary entries in the same hash key, or track expiry yourself (a separate sorted set keyed by insertion time, swept periodically) instead of reaching for EXPIRE and assuming it's field-scoped.
