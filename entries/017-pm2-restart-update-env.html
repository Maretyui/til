pm2 restart keeps the environment from the first pm2 start, not the current shell

A mail-sending SMTP password got rotated on the mail server. The deploy script for the app using it exports the new value from .env, rebuilds, then runs pm2 restart app-name like every other deploy before it. The app kept failing to authenticate with the old password anyway - after the rebuild, after the restart, after triple-checking the .env file on disk actually had the new value.

PM2 snapshots env at the first start, not at every restart

PM2's daemon captures the process environment once, at whatever moment the app was first brought under PM2 (pm2 start or an earlier deploy), and stores that snapshot internally. A plain pm2 restart app-name respawns the process using that stored snapshot, not the environment of the shell the restart command was actually run from. Exporting a fresh value right before the restart does nothing - PM2 never looks at the current shell's environment on a bare restart. 

# does NOT pick up a freshly exported var
export SMTP_PASS=new-value
pm2 restart app-name

# does
export SMTP_PASS=new-value
pm2 restart app-name --update-env

--update-env tells PM2 to re-capture the environment from the process running the restart command and overwrite its stored snapshot with it. Without that flag the restart is real - the process does cycle - it's just still running on stale credentials that look, from the outside, exactly like a caching problem somewhere else entirely.

The actual lesson

Any deploy step that changes environment variables and then restarts via PM2 needs --update-env on that restart, every time, not just on the first deploy. It's easy to write the flag once, copy the restart command into a different project's deploy recipe later, and quietly drop it - the failure mode isn't "restart didn't happen," it's "restart happened, but nothing actually changed," which sends debugging everywhere except the one line that mattered.
