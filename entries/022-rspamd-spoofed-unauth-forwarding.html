Rspamd silently drops internal relay mail that claims a local domain in From: without SASL auth

A mailing list had been quietly broken since the day it was set up: mail sent to the list address reached the list manager fine (Postfix logged a clean status=sent handoff), but none of the redistributed copies ever made it back out to subscribers. No bounce, no error visible anywhere from the sender's side — it just looked like "sometimes people don't get list mail."

The real cause: an anti-spoofing rule doesn't know about your own relay

Rspamd's spam-filtering layer runs a composite rule (SPOOFED_UNAUTH) that fires whenever a message's From:/envelope-from claims a locally-hosted domain but the connection isn't SASL-authenticated — a reasonable anti-spoofing default for mail arriving from the open internet. The problem: the list manager relays redistributed copies back through the same mail server internally, unauthenticated, and its From: legitimately uses the local domain. Rspamd couldn't tell that apart from an actual spoof attempt, scored it well past the reject threshold, and silently dropped every copy.

The fix

The mail stack (Mailcow/Rspamd in this case) has its own allowlist specifically for this situation — internal services that are allowed to relay mail claiming a local domain without SASL auth, keyed by source IP: 

redis-cli -a "$REDISPASS" HSET WHITELISTED_FWD_HOST \
  172.22.1.5/32 my-internal-relay-service

No Rspamd restart needed — the map is read live on every message. Verified before/after with Rspamd's own test tool against a sample message and source IP: 

rspamc --mime --from list-bounces@example.com --ip 172.22.1.5 symbols

The actual lesson

Any internal service that relays or redistributes mail on a mail server's behalf — a mailing list manager, an internal forwarder, a monitoring system emailing "from" the domain it's hosted under — needs to be explicitly allowlisted for unauthenticated local-domain relay, or a spoofing-prevention rule that's completely correct for internet-facing mail will silently eat every message it sends, with no bounce or error surfaced anywhere to explain why.
