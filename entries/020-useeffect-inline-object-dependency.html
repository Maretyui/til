an inline object in a useEffect dependency array reruns the effect every render

A component fetched data in a useEffect keyed off a filters object built from a couple of pieces of local state ({ category, sortOrder }). The network tab told the real story: the same request, fired on every single render, not just when category or sortOrder actually changed. No state update loop, no obvious re-render trigger in the component itself - the fetch was just never settling.

React compares dependencies by reference, not by value

useEffect's dependency array is checked with Object.is between renders - a shallow reference comparison, not a deep-equality check. An object or array literal written directly inside the render body ({ category, sortOrder }, or [a, b]) is a brand-new object every single render, even when every field inside it holds the exact same value as last time. Object.is sees two different references and considers the dependency "changed," so the effect reruns - which, if the effect itself triggers a state update (like storing fetched data), can also cascade into a render loop. 

// re-runs every render: {category, sortOrder} is a new object each time
useEffect(() => {
  fetchResults({ category, sortOrder });
}, [{ category, sortOrder }]);

// fine: primitives compare by value, not by reference
useEffect(() => {
  fetchResults({ category, sortOrder });
}, [category, sortOrder]);

// also fine if the object itself needs to be the dependency:
// memoize it so the reference is stable across renders
const filters = useMemo(() => ({ category, sortOrder }), [category, sortOrder]);
useEffect(() => {
  fetchResults(filters);
}, [filters]);

The same trap applies to inline arrow functions and arrays passed as dependencies, and to any object/array a parent passes down as a prop if that parent recreates it inline on every render too - the fix is the same either way, either depend on the underlying primitives directly or wrap the composite value in useMemo/useCallback so its reference is stable between renders that don't actually change its contents.

The actual lesson

A dependency array full of primitives is the safest default - React's comparison is reference-based, so anything that creates a new object, array, or function literal inline in the render body needs to be memoized before it's trustworthy as a dependency. "The effect keeps firing for no reason" is almost always this, not a state-management bug somewhere else in the component.
