cron runs jobs with a stripped-down PATH, not your login shell's

A shell script worked perfectly every time it was run by hand, then failed the moment it was dropped into a crontab - not with a permissions error or a stack trace, just a bare command not found for a binary that was unquestionably installed and on PATH in every interactive shell that touched the box.

cron doesn't source .bashrc/.profile at all

An interactive login shell builds its PATH by sourcing a chain of files - /etc/profile, ~/.bash_profile, ~/.bashrc, and whatever version manager (nvm, pyenv, rbenv) or package manager appended to it along the way. Cron never runs any of that. Each job executes under /bin/sh with a minimal, hardcoded environment - usually just PATH=/usr/bin:/bin - so anything installed into a user-local bin directory, a language version manager's shims, or even /usr/local/bin on some distros simply isn't found, even though which in a real terminal finds it instantly. 

# crontab -e
* * * * * some-tool --flag        # fails: "some-tool: command not found"

# two ways to actually fix it
* * * * * /full/path/to/some-tool --flag
PATH=/usr/local/bin:/usr/bin:/bin
* * * * * some-tool --flag

The safer of the two fixes is the absolute path - it doesn't depend on remembering to keep a hand-maintained PATH= line in sync with wherever tools actually get installed later. Worth checking with type -a some-tool or command -v some-tool from a plain sh invocation (not an interactive bash) to see what a cron job would actually resolve, before assuming the script itself is broken.

The actual lesson

A script that "works when I run it" but fails under cron almost always means the environment differs, not the script - cron's minimal, non-login, non-interactive shell is close to the least environment a command can run in on the whole system, and it's easy to forget that gap exists until a job silently stops doing anything at 4am with nothing but an exit code to show for it.
