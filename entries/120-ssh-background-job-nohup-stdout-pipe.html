A server start script kept dying seconds after the SSH session closed

A one-off game server process was launched over a single non-interactive SSH command, backgrounded so the connection could be closed right away: 

ssh host 'cd /srv/app && nohup ./start.sh &'

Despite nohup, the process reliably died a few seconds after the terminal closed — long enough to print its startup banner, not long enough to actually serve anything.

Why: nohup blocks the signal, not the broken pipe

nohup does exactly one thing: it makes the process ignore SIGHUP. It does nothing about where that process's stdout/stderr file descriptors point. In a one-off ssh host 'cmd' invocation without a pseudo-terminal, those descriptors are still the pipe back through the SSH channel itself. Closing the SSH session tears down that channel, and the next time the backgrounded process writes a log line to stdout, the write fails — SIGPIPE for anything that doesn't check the return value, a thrown I/O exception for anything that does, and either way the process exits. It was never the hangup that killed it; ignoring SIGHUP just meant the kill happened via its own output instead. 

ssh host 'cd /srv/app && nohup ./start.sh > server.log 2>&1 &'

The actual lesson

For anything launched over a non-interactive SSH command that needs to outlive the connection, nohup and redirecting stdout/stderr away from the session are two separate, both-required steps — one blocks the signal, the other detaches the file descriptors the signal was never going to save anyway. setsid is the more complete fix since it also drops the controlling terminal entirely, but the redirect alone is usually what was actually missing.
