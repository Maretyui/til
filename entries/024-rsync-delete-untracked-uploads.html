rsync --delete removes production files that were never in the local checkout

A normal deploy for a Next.js app: rsync the local git checkout up to the server with --delete so stale build artifacts and removed files don't linger, then rebuild and restart. 

rsync -avz --delete --exclude='.git' --exclude='node_modules' \
  --exclude='.next' . user@host:/var/www/app/

That app also had a small feature that let admins upload real files at runtime — PDFs, in this case — saved into a folder inside the project directory. Those files only ever existed on the server; they were never part of the git repo and never showed up in a local checkout at all.

Where it actually bit

--delete means "make the destination match the source exactly" — anything on the server that isn't present locally gets removed, no exceptions unless explicitly excluded. The uploads folder wasn't in the exclude list, so a routine content-only deploy quietly deleted every real, previously uploaded file on the very first sync — including one that had been uploaded that same day. The database row referencing it survived (the row lives in Postgres, untouched by rsync), so the app still linked to a file that no longer existed on disk.

The fix

rsync -avz --delete --exclude='.git' --exclude='node_modules' \
  --exclude='.next' --exclude='storage/uploads/' \
  . user@host:/var/www/app/

Any directory that holds real, server-only, runtime-generated state — user uploads, session files, anything not reproducible from the git history — needs its own explicit --exclude, the same way node_modules and build output already get excluded as a matter of habit.

The actual lesson

--delete doesn't know or care *why* a file exists only on the destination — a stale build artifact and a genuine user upload look identical to it. Before ever adding --delete to a new deploy script, walk the actual destination directory first and list every path that can contain real server-side state, not just the ones that come to mind — once one gets missed, the loss happens on the very next deploy, silently, with no confirmation prompt in between.
