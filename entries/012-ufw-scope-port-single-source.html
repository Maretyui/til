ufw can scope a port to one source IP instead of opening it to the whole internet

I needed to open a port on a box that's meant to only ever be reached through a reverse proxy sitting in front of it — a dev-preview port that a hostname's proxy config forwards to, nothing more. My first instinct was the usual one-liner: 

ufw allow 3000

Which works, in the sense that the proxy could now reach it. It also means literally anyone on the internet can reach it directly on that port, bypassing the proxy entirely — no TLS, no hostname routing, whatever's bound there just sitting open. Fine for a moment, easy to forget is still open later.

The narrower rule

ufw supports scoping a rule to a specific source, not just a bare port number: 

ufw allow from 192.168.178.28 to any port 3000 proto tcp

This only admits traffic whose source IP is the proxy box itself — everyone else's connection attempt to port 3000 on this host gets dropped before it reaches whatever's listening there. The proxy still works exactly the same as before; the only thing that changes is who else can reach the port directly.

Why it actually matters here

The whole point of routing something through a reverse proxy is usually TLS termination plus hostname-based routing — but none of that is actually enforced unless the backend port is also unreachable by any other path. A blanket ufw allow <port> on a "proxy-only" port quietly defeats that: an ad hoc test server bound to it (even something as throwaway as python3 -m http.server 3000 for a five-minute file handoff) is reachable by its raw IP:port from anywhere on the internet the whole time it's up, with no auth, whether or not the proxy hostname is even pointed at it.

The takeaway

For any port that's conceptually "only the proxy should ever hit this directly," scope the ufw rule to the proxy's actual IP from the start rather than opening it broadly and mentally filing it under "protected by the proxy." The proxy isn't a firewall — the firewall is.
