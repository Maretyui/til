A homemade rate-limit retry loop kept a bot hammering Discord for a full minute

A small helper wrapping raw REST calls (bulk role updates on a ticket bot) had its own 429 handler: read the retry hint off the response, wait that long, try again. It worked — but every retry loop was taking roughly a thousand times longer than the bucket it was supposedly respecting, and logs showed the bot still getting 429'd on the very next attempt after "waiting".

Why: the header and the body disagree on units

Discord's REST API returns rate-limit info in two places at once, and they don't match. The standard HTTP Retry-After header is in whole seconds, per the HTTP spec every other API also follows. But Discord's own JSON error body on a 429 also includes a retry_after field — and that one is a floating-point number of seconds too, which is easy to mistake for milliseconds if you're used to reading timestamps/durations as ms by default elsewhere in the same codebase. 

// A 429 response body looks like:
// { "message": "You are being rate limited.",
//   "retry_after": 0.847, "global": false }

// Wrong — treats 0.847 as milliseconds, retries almost immediately:
await sleep(body.retry_after);

// Right — it's already seconds:
await sleep(body.retry_after * 1000);

The actual bug here was the opposite mistake in the same codebase: a helper elsewhere read the Retry-After header (correctly, in seconds) but then multiplied it by 1000 a second time further up the call stack, where a generic "sleep for N seconds" utility was already doing that conversion — so a 2-second cooldown turned into a 2000-second one, and the bot just sat there for over half an hour looking hung.

The actual lesson

Both the header and the body value are seconds — never assume milliseconds just because a duration is stored as a plain number. Convert exactly once, as close as possible to the single place that actually calls setTimeout/sleep, and log the resolved wait time in a human-readable form ("waiting 2.3s") during development so a units mistake is obvious at a glance instead of only showing up as mysteriously long or mysteriously ineffective backoff.
