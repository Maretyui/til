A CI cache kept serving last week's dependencies after a lockfile change

A GitHub Actions workflow for a small monorepo cached node_modules keyed on a hash of the lockfile. After bumping a dependency in one package and pushing, the install step finished suspiciously fast and the old version was still what actually ran — the cache had been restored even though the lockfile had clearly changed. 

- uses: actions/cache@v4
  with:
    path: '**/node_modules'
    key: modules-${{ hashFiles('package-lock.json') }}

Why: hashFiles() only hashes the paths it's given, nothing more

package-lock.json as a bare pattern only matches the file at the repository root. The monorepo's actual lockfile changes were happening in packages/api/package-lock.json — a path the glob never touched. hashFiles() doesn't error or warn when a pattern matches nothing or only partially matches; it just hashes whatever it did find (in this case, nothing changed from the only file it was watching) and returns a cache key that looks perfectly valid. The workflow had no reason to suspect anything was wrong because every step reported success. 

key: modules-${{ hashFiles('**/package-lock.json') }}

The actual lesson

A recursive glob like **/package-lock.json is needed for any repo with more than one lockfile, and it's worth double-checking what a cache key pattern actually matches rather than assuming a single bare filename covers every workspace. A cheap sanity check: temporarily echo ${{ hashFiles('**/package-lock.json') }} as a build step output after any change to the cache config, and confirm the hash actually changes when a lockfile does — a stale cache fails silently, it never fails loudly.
