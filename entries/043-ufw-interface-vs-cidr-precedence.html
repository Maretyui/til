Restricting SSH to a mesh network locked a host out completely

Locking SSH down to VPN-mesh-only access on a small fleet of hosts seemed like a two-rule change: allow the mesh's CIDR range on port 22, deny everything else on port 22. On most hosts that worked exactly as expected. On one host it broke SSH entirely — not just from the LAN, but from the mesh too — requiring the hypervisor's console to fix. 

# the rule set that broke SSH on one host, worked fine on the others:
ufw allow from 100.64.0.0/10 to any port 22
ufw deny to any port 22

Why: an unscoped deny and a CIDR-scoped allow don't sort the way the rule numbers suggest

ufw status numbered shows rules in a clean top-to-bottom order, which reads like "allow wins because it's listed first." In practice a deny with no source restriction and an allow scoped only by a source CIDR didn't resolve in that intuitive order on this host — the deny effectively won for all traffic on that port, mesh included. The exact internal precedence isn't worth memorizing; the safer fix is to sidestep the ambiguity entirely. 

# the fix: scope both rules by network *interface* instead of by CIDR
ufw allow in on tailscale0 to any port 22 proto tcp
ufw deny in on eth0 to any port 22 proto tcp

The actual lesson

When restricting a port to one network path on a box that already has an allow-by-default policy, prefer interface-scoped rules (in on <iface>) over CIDR-scoped ones for both the allow and the deny. It reads exactly as intended — "only this NIC may reach this port" — and doesn't depend on how ufw resolves an unscoped rule against a scoped one for the same port. Worth testing from a second, already-open session before closing the one you're using, in case a host behaves like this one did.
