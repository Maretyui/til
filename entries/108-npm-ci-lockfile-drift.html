A deploy step failed on "npm ci" right after "npm install" had worked fine locally

A dependency got added with a plain npm install some-package, the app ran fine locally, and the change got committed. The deploy pipeline's build step — which runs npm ci instead of npm install for reproducible installs — failed immediately with npm ERR! Missing: some-package from lock file, even though package-lock.json clearly had just been touched by the same commit.

Why: the lockfile was stale, not missing

The install had actually run against a workspace where package-lock.json was briefly out of sync with package.json — a half-finished merge had left the lockfile a commit behind. npm install doesn't care: if it notices package.json and the lockfile disagree, it just resolves the difference and silently rewrites the lockfile to match, no warning printed. npm ci makes the opposite trade-off on purpose — it treats the lockfile as the single source of truth, does a strict equality check against package.json first, and refuses to resolve anything itself: 

# npm install: "these don't match, let me fix that for you"
npm install
git diff package-lock.json   # quietly rewritten, no error

# npm ci: "these don't match, that's your problem"
npm ci
# npm ERR! Missing: some-package from lock file
# npm ERR! Clean install a project

So the lockfile that got committed wasn't actually regenerated from the final package.json — it was a leftover from a half-done step, and nothing in a normal local workflow would ever surface that, because nobody runs npm ci by habit on their own machine.

The actual lesson

npm install and npm ci are not interchangeable "install my dependencies" commands — one heals a drifted lockfile, the other treats drift as a hard failure by design. Running npm ci locally before pushing (or at least npm install --package-lock-only followed by a diff check) catches this before a pipeline that uses ci does, instead of after.
