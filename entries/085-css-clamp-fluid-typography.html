A hero heading needed five breakpoints to stop looking wrong

A large hero heading had a fixed font-size that looked great at desktop width and comically oversized on a narrow phone. The instinctive fix was to add a media query per breakpoint, stepping the size down at each one — which worked, but meant five separate rules to maintain, and the heading still visibly "jumped" at each breakpoint edge instead of scaling smoothly.

Why: font-size can just be a formula instead of a table

clamp(min, preferred, max) takes three values and picks the middle one unless it would go outside the min/max bounds — and the "preferred" value can itself be a vw-based expression, so it scales continuously with viewport width instead of snapping at fixed steps: 

h1 {
  /* never smaller than 1.75rem, never larger than 3.5rem,
     otherwise scales with viewport width */
  font-size: clamp(1.75rem, 1.1rem + 3vw, 3.5rem);
}

The middle term is the part worth understanding: 1.1rem + 3vw means "a fixed base size plus 3% of the viewport width" — tune the fixed part to set roughly where the curve sits, and the vw coefficient to control how aggressively it grows. No media query needed at all; the min/max bounds are exactly what the breakpoint-based rules were doing manually, just continuous instead of stepped.

The actual lesson

Anywhere a value used to need "small screen: X, large screen: Y, with a couple of steps in between" — font-size, section padding, gap between grid items — clamp() with a vw-based preferred value is usually a direct, smaller replacement for the whole breakpoint ladder, as long as the relationship between viewport width and the value is meant to be roughly linear. It doesn't help when the layout needs to actually restructure (stack instead of scale), which is still a job for a real breakpoint.
