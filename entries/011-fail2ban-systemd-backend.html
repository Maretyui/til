fail2ban's auto backend detection silently fails to find sshd logs on older versions

I was doing a pass of installing fail2ban across a handful of hosts, all with the same sshd jail config that's worked everywhere else: bantime = 1h, findtime = 10m, maxretry = 5, drop it in jail.local, enable and restart the service, done. On an Ubuntu box this really is that simple. I assumed it'd be the same on a Debian-based Docker image running an older fail2ban (1.0.2) and moved on without double-checking.

The jail was never actually running

It wasn't until I went looking for banned IPs days later — fail2ban-client status sshd — that I noticed the jail wasn't in the jail list at all. The service itself was up (systemctl status fail2ban showed active/running, no crash, no obvious error), it had just never started the one jail I actually cared about. Digging through /var/log/fail2ban.log turned up the real message, logged once at startup and then never mentioned again: 

fail2ban.filter [1]: WARNING Have not found any log file for sshd jail
fail2ban.jail [1]: INFO   Jail 'sshd' is not started

Why the auto-detection missed it

fail2ban's default backend = auto tries several ways of finding the log to tail for a given jail — a plain log file first (/var/log/auth.log or similar), falling back to systemd's journal if nothing matches. Newer fail2ban versions handle this fallback correctly out of the box. On the older 1.0.2 build in this image, the file-based detection didn't find anything (Debian's base image logs sshd straight to the journal, no /var/log/auth.log at all) and the journal fallback just... didn't kick in — the jail quietly gave up instead of erroring loudly.

The fix

Set the backend explicitly instead of trusting auto-detection, right in the jail's jail.local stanza: 

[sshd]
enabled = true
backend = systemd
bantime = 1h
findtime = 10m
maxretry = 5

Restarted the service and fail2ban-client status sshd immediately showed the jail active and tailing real auth attempts.

The actual lesson has nothing to do with fail2ban specifically: installing and enabling a security tool isn't the same as confirming it's doing anything. "The service is running" and "the protection is active" are different claims — checking systemctl status told me the daemon was alive, not that the one jail I cared about was ever watching a log. Worth a five-second fail2ban-client status <jail> check right after any install, on any host, rather than assuming a clean install implies working protection.
