A config tweak via /reload left two plugins silently broken

A quick permissions config edit got applied with /reload instead of a full server restart, since restarting would have kicked everyone on at the time. Everything looked fine immediately after — the new permissions worked — but over the next hour two unrelated plugins started throwing errors on events they'd handled fine for days, and a scheduled task from a third plugin just stopped firing entirely.

Why: /reload only reloads plugin.yml files, not the JVM state behind them

/reload re-reads server.properties and plugin configs and re-registers plugin.yml entries, but it does not restart the JVM or give plugins a real unload/reload lifecycle the way a process restart does. Plugins that registered scheduled tasks, event listeners, or cached references to Bukkit's world/entity objects keep those old references around after the command line says "Reload complete" — some of which now point at half-replaced internal server state, since core server classes themselves aren't reinitialized consistently across that boundary.

/reload confirm

# a real process restart (systemctl restart, or just stopping and
# starting the server jar), which gives every plugin's onDisable()/

The actual lesson

Paper's own startup warning about /reload being unsupported isn't boilerplate caution — it's describing a real failure mode, not a hypothetical one. A config-only change that doesn't need new plugin code can usually be applied with a plugin-specific reload command instead (most expose their own /pluginname reload that only touches that plugin's own state); anything touching core server behavior is safer with a full restart during a maintenance window than with /reload at a "convenient" moment.
