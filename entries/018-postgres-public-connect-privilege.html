a fresh Postgres database is connectable by every role on the cluster unless you revoke it

A shared Postgres server hosts one database per app, each with its own dedicated owning role - the kind of setup that looks isolated at a glance because nobody hands out the other apps' passwords. Doing a real security sweep of that server turned up something not obvious from the role/ownership layout alone: any app's role could still open a plain psql -d other_apps_db connection using its own credentials, despite owning none of that database's tables.

CREATE DATABASE grants CONNECT to PUBLIC automatically

Postgres has a pseudo-role called PUBLIC that every login role implicitly belongs to, and by default a newly created database grants that pseudo-role CONNECT. It's not a misconfiguration anyone introduced - it's the out-of-the-box behavior of plain CREATE DATABASE. Per-table grants still apply once connected, so a stray role couldn't necessarily read anything - but being able to connect at all is already more surface than a "one database per app" setup is supposed to allow, and it's an easy detail to never think to check because nothing about the role-creation step calls it out. 

-- close the gap per database
REVOKE CONNECT ON DATABASE other_apps_db FROM PUBLIC;
GRANT CONNECT ON DATABASE other_apps_db TO the_owning_role;

Worth checking alongside this: whether app roles were also handed CREATEDB at some point (common if a role was originally created as a quick "just make it a superuser-lite" shortcut) - that privilege is cluster-wide too, letting a role spin up new databases of its own regardless of which one it's meant to own.

The actual lesson

"Each app has its own database and role" sounds isolated but isn't, by default - isolation is something you configure explicitly with REVOKE CONNECT ... FROM PUBLIC per database, not something you get for free just because the roles are separate. Worth a one-time audit on any shared Postgres cluster instead of assuming ownership boundaries imply connection boundaries.
