A "cancel on unmount" cleanup wasn't actually cancelling anything

A component fired a fetch() on mount and called controller.abort() in its cleanup function, the usual pattern for avoiding a "set state on an unmounted component" warning. The warning kept showing up anyway on fast navigations, as if the abort call was being ignored.

Why: abort() only matters while the request is still in flight

AbortController.abort() works by rejecting the controller's signal, which fetch() checks while the request is pending. Once a response has already come back and the fetch promise has settled - resolved or rejected - there is nothing left for the signal to interrupt. Calling abort() at that point does nothing and throws no error either; it's just a no-op. 

const controller = new AbortController();
const req = fetch(url, { signal: controller.signal });

req.then((res) => res.json()).then((data) => {
  setState(data); // this line can still run even if abort() is called
});                // right after, because the fetch already resolved

// later, in a cleanup function:
controller.abort(); // too late - does nothing, no error, no rejection

The actual race was in the .then() chain, not the fetch itself: the response could land in the gap between the network call finishing and the cleanup function running, and abort() has no power over code that already has the resolved value in hand.

The actual lesson

AbortController only prevents work that the fetch itself is still doing - it can't retroactively stop a .then() callback from running once the promise has already resolved. A component still needs its own "am I still mounted" guard (a ref flip on cleanup, checked before setState) alongside abort(), not instead of it.
