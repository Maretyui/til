Mailing-list redistribution silently vanished — twice

A self-hosted mail stack redistributes list mail through a separate list-manager container, which hands the message back to the main mail server to actually deliver to subscribers. The very first time this was wired up, every single redistributed copy got hard-rejected by the spam filter with a spoofing violation — the sender saw "delivered," but no subscriber ever received anything, and there was no bounce to notice. Fixed once by explicitly trusting the list-manager container's IP as an allowed internal relay. Weeks later, it broke again in exactly the same way, with no config changes on the mail side at all.

Why: a spam filter rule that only locally-hosted domains without authentication are allowed to claim, plus a container IP used as the trust boundary

The spam filter fires whenever a message claims a domain the server itself hosts in its From/envelope-from without real SMTP auth — correct behavior for anything arriving from the outside world, but it also catches a list manager relaying mail right back to the same server on the list's own behalf. The fix for that is a forwarding-host allowlist, which was set correctly... as a single container IP. That container got recreated (a routine restart), Docker's bridge network hands out addresses fresh each time, and the allowlisted /32 simply stopped matching anything real. Same root cause as hardcoding a container IP anywhere else, just discovered a second time in a different subsystem. 

# fragile — matches only until this one container is ever recreated
172.20.0.5/32  "list-manager - trusted relay"

# stable — survives any container restart/recreate on this network,
# and only the mail stack's own containers ever sit on it anyway
172.20.0.0/24  "mail-internal docker network - IP-stable"

The actual lesson

When a trust rule has to key off a container's address rather than its name, key off the whole subnet the relevant containers live on instead of one container's current IP — the subnet is stable, the IP inside it isn't. And when recovering from a "some mail is quietly never delivered" incident, don't stop at the fix: also clear out whatever penalty the outage itself accumulated (bounce counters, auto-disabled subscriptions) or the very next transient failure re-triggers the same symptom for everyone all over again.
