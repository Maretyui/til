A long list page rendered faster, then the scrollbar started fighting back

A page rendering a few hundred report cards in a single list got content-visibility: auto added to each card as a quick fix for a slow initial paint — the browser stops laying out and painting anything currently off-screen, which is exactly the win it promises. Initial load did get noticeably faster. But the scrollbar thumb started jumping around while scrolling fast, and "scroll to bottom" landed in the wrong place depending on how fast the scroll happened.

Why: an unsized off-screen element collapses, then snaps back

Without a hinted size, a content-visibility: auto element that's off-screen gets treated as having roughly zero intrinsic size until the browser actually lays it out — which only happens once it's close enough to the viewport to matter. That means the page's total scrollable height keeps changing as elements pop in and out of "skipped" state, which is exactly what a bouncing scrollbar thumb looks like. The fix is contain-intrinsic-size: a placeholder size the browser reserves for the element while its real content is being skipped, so the page's layout height stays stable even before that card has ever actually been rendered. 

.report-card {
  content-visibility: auto;
  /* reserve roughly the real rendered height up front, so
     off-screen cards don't collapse to ~0px and shift the
     scrollable area every time one enters or leaves view */
  contain-intrinsic-size: auto 220px;
}

The actual lesson

content-visibility: auto is close to a free win for long pages of repeated, similarly-sized blocks, but it's not a drop-in one-liner — it needs a matching contain-intrinsic-size estimate or it trades a slow first paint for a visibly unstable scrollbar. The size only needs to be roughly right; it's a layout placeholder, not a hard constraint on the eventual rendered content.
