ufw's CIDR-scoped allow and an unscoped deny for the same port don't behave like rule order implies

Trying to restrict SSH to just a VPN mesh range, the plan looked simple: allow port 22 from the mesh CIDR, then deny port 22 from everywhere else, added in that order so the more specific rule would win. 

ufw allow from 100.64.0.0/10 to any port 22
ufw deny to any port 22

This looked correct and matched a pattern that had already worked fine on another host. On this particular box it broke SSH completely — not just for LAN clients that were supposed to be blocked, but for the mesh clients that were supposed to stay allowed too. No console access meant recovering it needed the hypervisor's own virtual console, not SSH.

The fix: match on interface, not source CIDR

Instead of scoping the allow rule by source address, scope both rules by which network interface the packet actually arrives on: 

ufw allow in on tailscale0 to any port 22 proto tcp
ufw deny in on eth0 to any port 22 proto tcp

Interface-scoped rules apply cleanly regardless of rule ordering quirks between an unscoped deny and a CIDR-scoped allow for the same port — each rule only ever evaluates traffic on its own named interface, so there's no shared/ambiguous rule to reconcile in the first place.

The actual lesson

When a firewall rule pair needs "allow from trusted network, deny from everything else" on the exact same port, prefer interface matching (in on <iface>) over CIDR matching if the trusted network already maps to its own interface (a VPN mesh, a Docker bridge, a VLAN). It sidesteps a whole class of allow/deny-precedence surprises that CIDR-only rules can hit — worth testing from a second connection before closing the one you're currently using either way.
