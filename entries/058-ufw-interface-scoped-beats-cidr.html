The exact rule that worked on one box locked out another

Restricting SSH to a private mesh network across a handful of Linux hosts, the plan was: allow port 22 from the mesh's subnet, then deny it from everywhere else. On the first host this worked fine using rules scoped by source CIDR — ufw allow from 100.64.0.0/10 to any port 22 followed by ufw deny to any port 22. Copying the exact same two rules to a second host broke SSH completely, from both the mesh and the LAN, requiring a console session to fix — not the intended "mesh only" outcome, but "nobody."

Rule precedence between an unscoped deny and a scoped allow isn't just "first match wins" the way it looks

ufw is a thin layer over iptables, and how an allow/deny pair for the same port interacts depends on more than just which rule number comes first — a completely unscoped deny for a port and a CIDR-scoped allow for that same port do not always resolve the way the rule list order implies. The fix that actually held, on every host, was switching from CIDR matching to interface matching instead: ufw allow in on tailscale0 to any port 22 paired with ufw deny in on eth0 to any port 22 (using each host's real LAN interface name). Traffic arriving on the mesh interface and traffic arriving on the LAN interface are unambiguous to the kernel in a way that "does this source IP fall inside this /10" apparently wasn't, in combination with an unscoped deny for the same port.

The actual lesson

When a host needs to accept a service on one network path (mesh, VPN, a specific NIC) and reject it on another, prefer ufw ... in on <interface> rules over CIDR-scoped ones for both the allow and the deny — it removes the ambiguity entirely instead of relying on rule-order intuition that turned out not to hold consistently across hosts with otherwise-identical firewall state.
