Wings derives its websocket CORS origin from its own config, not the node's

Setting up Pelican (a game-server control panel) behind a reverse proxy, the live console in the browser kept failing to connect — the panel's server list, file manager, everything else worked, but the console websocket silently 403'd with no useful message in the browser devtools.

The panel's node settings (FQDN, scheme, "behind proxy" flag) were all correct, and I'd regenerated Wings' config from the panel after setting them, so I assumed the two were in sync. They weren't.

The actual mismatch

Wings (the daemon that actually runs the game server containers) reads its own /etc/pelican/config.yml, and specifically its remote: field, to decide what origin is allowed to open a websocket connection to it. Regenerating the config from the panel is supposed to fill this in automatically, but after a manual edit earlier in the setup it had drifted to a plain http:// URL while the panel itself was serving over https://: 

# wrong — doesn't match the public https origin the browser sends
remote: http://games.example.com

# correct
remote: https://games.example.com

Since the browser builds the console's websocket URL from the page it's actually loaded on (wss://... for an HTTPS page), a scheme mismatch here is enough to fail Wings' own origin check — and it fails silently, with nothing browser-side pointing at the real cause.

The fix

Regenerate the node's config from the panel and double-check the remote: line matches the panel's actual public URL — scheme included — before assuming the problem is somewhere in the reverse proxy: 

php artisan p:node:configuration <node-id> > /etc/pelican/config.yml
grep remote: /etc/pelican/config.yml
systemctl restart wings
