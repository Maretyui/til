A truncated preview started ending in a broken glyph

A "show a short preview, then an ellipsis" feature truncated user text with plain str.slice(0, 40) + "…". It worked fine for months, then a preview that happened to cut off right after a family emoji or a flag emoji started rendering a stray tofu box or a lone skin-tone modifier with nothing to attach to — the emoji had been sliced clean in half.

Why: JS string indices count UTF-16 code units, not "characters"

What a person perceives as one character — a flag, a family emoji, a letter with a combining accent — is often built from multiple Unicode code points stitched together with zero-width joiners or regional indicator pairs, and some of those code points are themselves surrogate pairs in UTF-16. String.prototype.slice and .length have no idea any of that grouping exists; they just count 16-bit units and cut wherever the requested number lands, even if that's in the middle of one visual glyph.

The fix is Intl.Segmenter, which understands Unicode's actual grapheme-cluster boundaries — the same rules a text editor uses to decide where the cursor is allowed to land: 

function truncateGraphemes(str, maxGraphemes) {
  const segmenter = new Intl.Segmenter(undefined, { granularity: "grapheme" });
  const graphemes = [...segmenter.segment(str)].map((s) => s.segment);
  if (graphemes.length <= maxGraphemes) return str;
  return graphemes.slice(0, maxGraphemes).join("") + "…";
}

Segmenting first and then slicing the resulting array means the cut always lands on a real grapheme boundary — a whole flag or a whole family emoji, never half of one.

The actual lesson

Any string length limit, truncation, or "characters remaining" counter that has to survive real-world Unicode (emoji, combining accents, non-Latin scripts) shouldn't index by .length or slice by raw position. Segment first with Intl.Segmenter, then count or slice the segments — it's a native browser API, no library needed, and it fixes the bug at the root instead of special-casing specific emoji ranges.
