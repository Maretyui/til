A "skip Sundays" cron rule quietly also skipped Sundays twice a week on paper, and once for real

A nightly job needed to run every day except Sunday, so the day-of-week field got written as a range that explicitly excluded what looked like the one day it shouldn't run on. The job still fired correctly every day — the surprise was on the monitoring side, where a dashboard built from the same cron expression listed Sunday as a run day under one interpretation and not under another, because two different tools disagreed about what number Sunday even is.

Why: the day-of-week field has two valid spellings for Sunday

Standard cron syntax allows 0 and 7 for Sunday in the day-of-week field — both are valid, both mean the same day, and most cron implementations accept either without complaint. The field otherwise runs Monday–Saturday as 1–6, so it's easy to assume the week just wraps from 6 back to 0 and stop there, never noticing 7 is also live. A hand-written range like 1-6 for "weekdays plus Saturday" is correct either way, but a tool that generates or parses cron expressions and only normalizes one of the two spellings will misreport schedules that use the other — exactly the dashboard mismatch that surfaced this, not a broken job. 

# Both of these mean "every day except Sunday" - 0 and 7 are
# interchangeable for Sunday, not two different days
0 3 * * 1-6
0 3 * * 1,2,3,4,5,6

# A naive parser that only checks for "7" to mean Sunday will
# misclassify this as including Sunday, since it also matches 0
0 3 * * 0,1,2,3,4,5,6

The actual lesson

Writing cron expressions by hand, stick to one spelling consistently (most people default to 0) so the expression at least reads unambiguously. Writing code that parses or generates them, normalize both 0 and 7 to the same value up front — treating only one of them as "real" Sunday is the kind of bug that stays invisible until two tools built against different assumptions are compared side by side.
