"Host key verification failed" for a name, but the IP connects fine

A server was reachable and already fully trusted at its IP address — ssh 192.0.2.10 connected without any prompt at all, key already accepted long ago. Reaching the exact same box by a short internal hostname alias instead, e.g. ssh app-host, failed immediately with Host key verification failed, as if it were a completely different, untrusted machine.

Why: known_hosts keys by name, not by identity

OpenSSH's known_hosts file stores one entry per hostname-or-IP string a client actually typed, each paired with the fingerprint it saw the first time. It does not track "this is the same physical host reachable multiple ways" — an IP and a name that both point at one machine are, as far as known_hosts is concerned, two entirely separate identities until each one has been accepted on its own. This is not a sign of a key mismatch or a man-in-the-middle — it is simply a name that has never been seen before, checked with the wrong mental model (comparing keys) instead of the right one (comparing the two lines in the file). 

ssh-keygen -F app-host      # nothing — never connected under this name
ssh-keygen -F 192.0.2.10    # shows the already-trusted fingerprint

Fix: add the alias, don't chase a key mismatch

Confirm both fingerprints are identical (they will be — same host), then just connect once by the new name and accept it, or add the alias explicitly: 

ssh -o StrictHostKeyChecking=accept-new app-host
# or maintain both entries deliberately in ~/.ssh/config

Whichever hostnames or IPs are actually used to reach a box need their own accepted entry — trusting one form doesn't propagate to the others.
