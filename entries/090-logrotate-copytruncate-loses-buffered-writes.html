A log file's last few lines before a rotation kept disappearing

A long-running service logged to a plain file, rotated nightly by logrotate with the copytruncate option. Every so often, the last handful of lines written right around rotation time were just gone from both the old (copied) file and the new one — not corrupted, not misordered, just missing.

Why: copytruncate doesn't coordinate with the writer at all

The normal logrotate approach is to rename the file and send the process a signal (or reload it) so it reopens a fresh file handle at the new path. copytruncate exists for processes that can't be told to reopen their log file — instead, logrotate copies the current contents to a new file, then truncates the original in place so the process's already-open file descriptor keeps writing into it.

The problem is the gap between the copy and the truncate. If the process has data sitting in a stdio write buffer that hasn't been flushed to the file yet at the moment of the copy, that data is not in the copy - and then the truncate discards it from the original too, since it never actually reached disk in time. It isn't a race in the sense of corrupting bytes; the data simply never existed in either file at the instant logrotate looked. 

logrotate config using copytruncate:

/var/log/myapp/*.log {
    daily
    copytruncate   # <- no signal sent, no reopen; just copy + truncate
    rotate 7
}

The actual lesson

copytruncate is a compatibility fallback, not a free lunch - it trades a small, unavoidable window of possible data loss for not having to modify or signal the writing process. If the process can be made to reopen its log file on SIGHUP (or via a reload command), the normal create/rename-based rotation is strictly safer and should be preferred; copytruncate is only the right call when that's genuinely not an option.
