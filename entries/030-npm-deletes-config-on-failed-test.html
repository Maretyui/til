Nginx Proxy Manager can silently delete a working config on save

Edited an existing, working proxy host in Nginx Proxy Manager's admin UI — just adding a custom location, nothing exotic. Saved it, and the site immediately started failing TLS handshakes with ERR_SSL_UNRECOGNIZED_NAME_ALERT. The proxy host record in NPM's own UI still showed every setting correctly; nothing in the database looked wrong at all.

NPM deletes the old file before it knows the new one is valid

NPM's save flow regenerates the host's nginx config file from scratch on every edit. Its actual sequence is: delete the existing .conf file, write a new one from the updated database record, then test it with nginx's own config check. If that test fails, NPM does not restore the previous working file — it just leaves the file deleted and logs the failure to an internal metadata field that never surfaces anywhere in the UI. From nginx's perspective there's simply no server block left for that hostname's SNI at all, which is exactly what produces an "unrecognized name" TLS error instead of a more obviously config-related one.

Confirming it

Checked directly inside the NPM container: 

docker exec npm-app-1 ls /data/nginx/proxy_host/

The file for that host's ID was genuinely missing, even though the UI's edit form still rendered every field as if it were live.

The fix

Rebuilt the config file by hand from the database record (NPM's SQLite file, mounted on the host) and dropped it straight into the container, then verified and reloaded manually: 

docker cp fixed-host.conf npm-app-1:/data/nginx/proxy_host/28.conf
docker exec npm-app-1 nginx -t
docker exec npm-app-1 nginx -s reload

The actual lesson

A proxy host that "looks correct" in NPM's admin UI after a save isn't proof the underlying nginx config actually exists — the UI reflects the database, not the generated file on disk, and NPM's own failure-recovery path silently leaves nothing behind instead of restoring the last-known-good config. If a host starts failing TLS right after an edit, check for the actual .conf file inside the container before assuming it's a certificate or DNS problem.
