An LXC container's runaway process can freeze the whole Proxmox host

A player on one of my Minecraft servers built a carpet-based item duplicator, and it worked a little too well — it started spawning a huge number of item entities in one chunk. The server running that world lives in a Proxmox LXC container, and within a few minutes the container's memory usage ballooned way past what the world normally needs.

What I didn't expect: it wasn't just that one container that froze. The entire physical host locked up — every other guest on the same machine (a reverse proxy, a database, a mail server, a VPN hub) became unreachable at the same time, and it took two hard power-cycles to bring things back.

Why an LXC is different from a VM here

A VM gets its own kernel and a hard memory ceiling enforced by the hypervisor no matter what. An LXC container shares the host's kernel directly — it's closer to a fenced-off set of processes than a fully isolated machine. If a container's configured memory limit is generous (or the host is memory-overcommitted across guests, as mine was), a single process inside it going wild can still pressure the host's real memory and IO enough to stall everything else, LXC or not.

The fix

Right-size the memory limit on every guest so no single one can eat a large fraction of the host's physical RAM, even under overcommit: 

# Proxmox UI: guest -> Hardware -> Memory -> set a hard cap
# or via CLI:
pct set <ctid> -memory 16384

The underlying item pile in the Minecraft world itself is still there — this only stops a repeat from taking the whole host down. If that container starts crashing again, it should now crash on its own (a contained Java heap OOM), not drag every other guest down with it.
