a settings-page field for TRUSTED_PROXIES doesn't mean it's actually wired up

A self-hosted Laravel panel sits behind a reverse proxy that terminates TLS, and it ships with exactly the setting you'd expect for that: an admin settings page field called "Trusted proxies", plus a TRUSTED_PROXIES env var and a config/trustedproxy.php file to hold it. Filling it in with the proxy's LAN IP felt like the whole job.

It wasn't. A Livewire file upload (a server icon, using a signed URL under the hood) started failing with a silent 401 - the signature just didn't match. That's the classic symptom of a Laravel app not trusting its proxy: without trusting the proxy's forwarded headers, the app builds signed URLs against the wrong scheme/host (plain HTTP instead of the real HTTPS the browser actually used), so the signature it generates and the one it later verifies never agree.

The setting existed. The code reading it didn't.

Grepping the actual application code turned up the real problem: nothing in bootstrap/app.php ever called Laravel's trustProxies(). The config file and the env var existed, and the admin UI dutifully saved whatever was typed into it - but nothing downstream ever read that value into the framework's actual proxy-trust middleware. A config field can exist as pure plumbing with no destination. 

// bootstrap/app.php
->withMiddleware(function (Middleware $middleware) {
    $middleware->trustProxies(
        at: array_filter(explode(',', (string) env('TRUSTED_PROXIES', '')))
    );
})

Adding that one call - reading the same env var the settings page already wrote to - fixed the signed URL mismatch immediately.

The actual lesson

When a symptom looks like "the app doesn't trust the proxy", don't stop at confirming the relevant setting is filled in somewhere. Grep for where that setting is actually consumed. A field in an admin UI, a documented env var, even a dedicated config file are all just evidence that someone planned to wire it up - not proof that anyone finished the job.
