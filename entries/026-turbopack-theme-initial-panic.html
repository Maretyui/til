a stray --radius-*: initial; in a Tailwind v4 @theme block crashes Turbopack's dev server

Mid-way through a design pass on a Next.js 16 + Tailwind v4 project, the dev server (Turbopack) started hard-crashing on every single request — not a normal Next.js error overlay, a full process-level panic in the Rust compiler itself: 

turbo-tasks-backend panic: "Every task must have a task type"

Once the panic happened, every subsequent page load 500'd with a completely unrelated-looking error from the Next.js side: 

TypeError: components.ComponentMod.handler is not a function

That second error is what actually showed up in the browser, which sent the first debugging instinct down the wrong path entirely — it looks like a routing/module-resolution bug, not a CSS problem.

Where it actually came from

The real cause was a single line added to globals.css's Tailwind v4 @theme inline block while trying to reset a custom radius token: 

@theme inline {
  --radius-*: initial;
}

That's valid-looking Tailwind v4 theme syntax on paper (the wildcard-reset pattern exists for other namespaces), but something about it — combined with how Turbopack's incremental task graph caches theme-derived CSS — reliably tripped the "every task must have a task type" invariant inside turbo-tasks-backend. Clearing .next did not help, which was the first strong hint the cache itself wasn't the problem.

The fix

Just deleting that one line fixed it immediately — no cache clear, no dev server restart even needed beyond the automatic Turbopack recompile that followed the file save.

The actual lesson

If a Turbopack dev server starts panicking or every route starts 500ing with a generic, unrelated-looking module error right after editing globals.css or an @theme block, suspect the CSS edit itself before chasing routing/module code — and don't waste time on .next cache clears first, since this class of bug isn't cache state, it's the compiler choking on the source.
