docker compose --force-recreate wipes anything installed into a container's writable layer

While experimenting with a WordPress container as a headless CMS, wp-cli got installed straight into the running container with a quick curl-to-/usr/local/bin one-liner, the same way you'd install a tool on a normal VM. It worked fine for a while — until an unrelated docker compose up -d --force-recreate (done to pick up a changed environment variable) came back with wp: command not found, as if it had never been installed at all.

Named volumes and bind mounts survive; the container's own layer doesn't

The WordPress files themselves (the actual site content, uploaded media, the custom plugin directory) were untouched — those live in a named volume and a bind mount respectively, both of which are external to the container and explicitly preserved across a recreate. But --force-recreate does exactly what it says: it throws away the old container (including its writable layer) and creates a fresh one from the image, so anything installed imperatively into that layer — a curl'd binary, an apt install run by hand inside a shell, etc. — is gone, with no warning that it's about to happen. 

# this looks like a normal restart, but it's actually a full recreate:
docker compose up -d --force-recreate

# survives: named volumes, bind mounts (declared in docker-compose.yml)
# does NOT survive: anything installed by hand into the container itself

The actual lesson

Anything a container needs long-term belongs in the image (a Dockerfile layer) or an entrypoint script that reinstalls it on every start — not a one-off manual install into a running container, even one that's expected to stay up for a while. Treat --force-recreate (and any other flow that replaces the container rather than just restarting the same one) as a reminder to reinstall one-off tooling, not a bug when it quietly disappears.
