A daily cleanup job just never ran after a box was rebooted for maintenance

A systemd timer set to run a log-rotation script once a day (OnCalendar=daily) went quiet for almost a week after a machine was taken down for an evening and brought back up the next morning. No error anywhere — systemctl list-timers showed a perfectly normal "next run" time, just nothing had actually executed in between.

Why: a calendar timer only fires while something is watching the clock

OnCalendar= timers are evaluated against wall-clock time by a running systemd instance — if the box is powered off (or just the timer unit was disabled) at the exact moment a scheduled run was due, that run simply never happens. Unlike an OnUnitActiveSec= timer counting elapsed time since the last run, systemd does not remember "this was supposed to fire yesterday at 3am" and catch up once it's back — the missed occurrence is gone unless you explicitly ask for that behavior. 

[Timer]
OnCalendar=daily
# Without this, a run scheduled during downtime is skipped
# entirely instead of firing once as soon as the system is
# back up:
Persistent=true

[Install]
WantedBy=timers.target

Persistent=true makes systemd record the last trigger time (via the timer's stamp file under /var/lib/systemd/timers/) and, on startup, check whether a scheduled run was missed since then — if so, it fires once immediately instead of waiting for the next regularly scheduled slot. It's the timer-unit equivalent of cron's anacron, and it's off by default.

The actual lesson

Any OnCalendar= timer covering something that has to happen exactly once per period — rotation, backups, cleanup — needs Persistent=true on any machine that might ever be rebooted, suspended, or briefly down across a scheduled run. systemctl list-timers only tells you the next scheduled time; it says nothing about whether a past one was actually honored.
