a docker-compose WP_SITEURL constant silently overrides wp-cli option changes

Standing up a headless WordPress container behind a reverse proxy, the site's URL needed to change from the container's default to the real dev hostname. The obvious move: fix it with wp-cli. 

wp option update siteurl 'https://dev.example.com'
wp option update home 'https://dev.example.com'

wp option get siteurl immediately echoed back the new value, so it looked like it had worked. Every actual page load still generated links pointing at the old default host, as if the change had never happened at all.

Where it actually bit

The compose file's WORDPRESS_CONFIG_EXTRA environment variable already had define('WP_SITEURL', ...) and define('WP_HOME', ...) baked in from the initial scaffold. In WordPress, a define()'d constant always wins over the same-named row in the wp_options table — and wp-cli's own option get reads back the *effective* value (the constant), not the row it just wrote. So the update genuinely succeeded at the database level, and wp-cli's own confirmation was completely accurate — it just wasn't telling the whole story, since the constant silently overrides it for everything that actually renders a page.

The fix

# in docker-compose.yml
environment:
  WORDPRESS_CONFIG_EXTRA: |
    define('WP_SITEURL', 'https://dev.example.com');
    define('WP_HOME', 'https://dev.example.com');

Editing the actual source of truth and recreating the container (a restart alone doesn't re-read the compose file's environment block) fixed it for real — after that, both the constant and the option row agreed, and pages started linking to the right host.

The actual lesson

If a WordPress setting seems "stuck" despite wp-cli confirming the update took, check for a define()'d constant of the same name before assuming the database write silently failed — wp_SITEURL/WP_HOME are the classic examples, but the same constant-wins-over-option rule applies to anything else a scaffold or hosting config defines up front.
