Several healthy domains went down together, all sharing one certificate

A handful of unrelated-looking domains started serving an expired TLS certificate at the same time. Nothing about their own DNS or web server config had changed recently, which made it look like several independent failures happening to line up on the same day.

Why: they were all Subject Alternative Names on one certificate order

A single Let's Encrypt certificate can cover many hostnames at once via its Subject Alternative Name (SAN) list, and renewal requests all of them together as one order. One of the names on that list had been decommissioned — its DNS record was gone — but it had never been removed from the certificate's SAN list. Certbot's HTTP-01 challenge has to succeed for every single name in the order, so the one unreachable name failed the whole renewal, and every other perfectly healthy domain sharing that certificate expired right along with it. 

# the renewal log shows the real reason near the top, not the
# generic failure summary at the very end:
grep -E '"detail"|Challenge failed for domain' letsencrypt.log

# removing one SAN isn't something `certbot renew` can do —
# it needs a fresh order with the reduced name list:
certbot certonly --cert-name mycert --authenticator webroot \
  --webroot-path /var/www/acme-challenge \
  -d still-live-a.example.com -d still-live-b.example.com
  # (dead-name.example.com deliberately left out)

The actual lesson

A multi-SAN certificate is a single point of failure shared by every hostname on it, not just a convenience for grouping related domains under one order. Decommissioning a domain should include pruning it from any certificate's SAN list immediately, not just deleting its DNS record and reverse-proxy entry — otherwise the next routine renewal is the thing that quietly takes down everything else riding along with it.
