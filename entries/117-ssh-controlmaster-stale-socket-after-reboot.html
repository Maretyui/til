Every new SSH session hung for a while, then connected, right after a host came back up from a reboot

A box went down for a quick reboot. Once it was back and pingable, every ssh into it from one particular machine stalled for around 15 seconds before finally connecting — but only from that one machine. Fresh connections from anywhere else worked instantly. Deleting and re-running the command made no difference; it hung every single time until the stall timed out on its own.

Why: ControlMaster was still holding a socket to a connection that no longer existed

That one machine had ControlMaster auto configured for connection multiplexing, so the very first SSH session to that host had opened a persistent control socket and every later session was reusing it instead of opening a new TCP connection. The reboot killed the remote sshd process the socket pointed at, but the local control socket file itself survived untouched — ssh had no way to know the other end was gone until it tried to use it, which is exactly the ~15 second hang: a dead TCP connection with no reset packet to report it, so the client just waited out its own timeout before giving up on the stale multiplexed session and opening a fresh one. 

# find and kill the stale control socket by hand
ssh -O check user@host
ssh -O exit user@host

The actual lesson

ssh -O check reports whether a given host still has a live control socket, and -O exit tears it down without needing to wait for the hang. The cleaner fix is a ControlPersist value with a short idle timeout (e.g. ControlPersist 30s) instead of leaving the master connection open indefinitely — it still gets the multiplexing speedup for a burst of commands, but a socket left over from before a remote reboot doesn't linger around to cause a confusing one-off hang days later.
