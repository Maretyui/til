re-signing an Android app with a different keystore makes the OS treat it as a different app

Porting a Go/Fyne desktop app to Android via gomobile, the first working build was debug-signed - fine for a quick sideload test on a real device over a temporary local HTTP server. Once the app was confirmed working, the next step was building the real -release variant with a proper keystore (keytool-generated, stored safely for future rebuilds).

Installing that release build over the existing debug install failed immediately with a blunt App not installed, no further explanation in the UI.

Same package name, different signature, no upgrade path

Android identifies "the same app" by package name and signing certificate together, not package name alone. The debug build had been signed with Android's own ephemeral debug key; the release build was signed with the brand new keystore. Same applicationId, completely different signer - as far as the OS is concerned that's not an update, it's a different app that happens to claim the same identity, and it refuses to overwrite the existing install rather than silently trusting the swap.

The fix in the moment was just uninstalling the debug build first, then installing the release APK fresh. But that's genuinely only viable because it was still pre-launch testing with no real user data at stake.

Why this only bites once

This is strictly a first-transition problem. Every build going forward - each rebuild, each update - reuses that same release keystore, so the signature stays consistent and normal in-place updates work exactly as expected. It's only the debug-to-release switch (or any future switch to a different keystore) that triggers it. Which is also exactly why the keystore file and its password get saved somewhere durable the moment they're generated: losing that file doesn't just cost a rebuild, it means every future release is permanently locked out of updating everyone who already has the app installed.
