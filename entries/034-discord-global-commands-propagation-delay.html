Discord global slash commands can take up to an hour to propagate

Testing a new ticket-bot command with client.application.commands.set(commands) instead of the usual guild.commands.set(commands) made the command vanish from the picker in the test server for a while — not a permissions issue, not a bad payload, the registration call itself returned 200 with the new command listed in the response body.

Guild-scoped vs. global registration

guild.commands.set() registers commands against a single guild ID and updates there essentially instantly — this is why every bot's dev workflow (and this fleet's own ticket-core test deployment) registers commands per-guild rather than globally. client.application.commands.set() (or the REST equivalent hitting /applications/{id}/commands with no guild ID) registers them for every server the bot is in at once, and Discord's own docs are explicit that global updates "can take up to an hour" to reach all guilds — there's no webhook or event that fires when propagation finishes, it just eventually shows up. 

// instant, one guild only — normal for dev/test
await guild.commands.set(commands);

// accepted immediately, but the picker update itself
// can lag up to ~1 hour across every guild the bot is in
await client.application.commands.set(commands);

The actual lesson

A 200 from the global command registration endpoint means Discord accepted the definition, not that it's live everywhere yet. Keep using guild-scoped registration for any server where a command needs to appear immediately (test guilds, a single-server bot), and only reach for the global endpoint for a bot running in many guilds where the propagation delay is an acceptable tradeoff for not re-registering per guild.
