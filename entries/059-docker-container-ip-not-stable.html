Two game server containers swapped addresses and started answering for each other

A Velocity-style Minecraft proxy config pointed at a couple of backend game server containers by hardcoded bridge-network IP — something like 172.18.0.2:25566 for one server and 172.18.0.3:25566 for another. It worked fine right up until an unrelated round of container restarts, after which players trying to join one server landed on the other, and the proxy logs started showing intermittent Connection refused / NoRouteToHost errors that looked exactly like a flaky network, not a config problem.

Why: Docker's bridge-network IP assignment isn't sticky across restarts

Docker hands out bridge-network IPs from a pool at container start, in whatever order containers happen to come up — nothing guarantees the same container gets the same address twice. Two containers restarting in a different order than usual was enough for their addresses to literally swap, and a proxy config written against a fixed IP had no way to notice the ground had shifted under it. 

# fragile — an IP that only happens to be correct right now
[servers]
survival = "172.18.0.2:25566"

# stable — Docker's own embedded DNS resolves the container's name
# (or a fixed identifier assigned to it) to whatever its current IP is
[servers]
survival = "survival-backend:25566"

The actual lesson

Never hardcode a container's bridge-network IP into another service's config, even one that "hasn't changed in months" — use the container's own name (or another stable identifier Docker's built-in DNS can resolve) instead. It costs nothing on a healthy network and completely removes this class of bug, which otherwise only ever shows up after the fact, disguised as a networking problem rather than a config one.
