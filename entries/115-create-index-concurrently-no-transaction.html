A migration file with two statements in it failed on the second one

The goal was to add an index without locking writers out for the full build time, so the migration used CREATE INDEX CONCURRENTLY. It worked fine run by hand at the psql prompt. Wrapped in a migration file that ran both statements inside one transaction, it failed immediately: 

BEGIN;
CREATE INDEX CONCURRENTLY idx_events_user_id ON events (user_id);
ALTER TABLE events ADD CONSTRAINT events_user_id_fkey
  FOREIGN KEY (user_id) REFERENCES users (id);
COMMIT;
-- ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block

Why: the whole point of CONCURRENTLY is two separate transactions

A normal CREATE INDEX takes a lock that blocks writes for the whole build and does it as one transaction. The CONCURRENTLY variant avoids that lock by scanning the table twice in two separate transactions, with a wait in between for any transactions that were already in flight when it started. That's structurally incompatible with being wrapped in an outer transaction — there's no "one transaction" for it to join, so Postgres refuses outright rather than silently falling back to a blocking build.

The actual lesson

Migration tools that auto-wrap every migration in a transaction (so a failure rolls back cleanly) need a per-migration opt-out for any statement using CONCURRENTLY, and that statement has to be the only one in its migration — it can't share a file with other DDL that still wants transactional safety. It also can't be rolled back automatically on failure: a crashed concurrent build leaves an INVALID index behind that has to be dropped and rebuilt by hand, it isn't cleaned up for you.
