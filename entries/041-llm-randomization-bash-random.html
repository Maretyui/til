A daily cron prompt said "pick a random number of repos to touch"

A daily automation script prompts an LLM to decide how many repos to touch out of a fixed pool, phrased as "pick a random count between 1 and N." Looking back over several weeks of run logs, the chosen count wasn't random at all — it converged hard on the same single number, run after run, with only rare deviation.

Why: sampling from a prompt isn't sampling from a distribution

An LLM asked to "choose randomly" is still doing next-token prediction over the text of its own answer, not calling a real RNG. Whatever number reads as the most typical, unremarkable "random-sounding" choice for that phrasing ends up dominating the output distribution — the model has no access to actual entropy unless something outside it supplies one. 

# doesn't reliably vary run to run:
# "pick a random number between 1 and 11"

# does, because the randomness comes from outside the model:
TOUCH_COUNT=$(( (RANDOM % 11) + 1 ))
echo "$TOUCH_COUNT" # fed into the prompt as a fixed instruction, not a choice

The actual lesson

If a script needs a value to genuinely vary, generate it with a real source of randomness ($RANDOM, shuf, /dev/urandom) outside the model and hand it to the prompt as a already-decided instruction, rather than asking the model to invent the number itself. This applies to anything where uniform-looking output would be a red flag — variable commit counts, sampled test data, jittered retry delays — not just this one cron job.
