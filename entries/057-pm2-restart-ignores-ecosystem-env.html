The file on disk was right, the running process wasn't

An API's ecosystem.config.js had a DATABASE_URL pointed at the correct database host — checked it twice, definitely correct. Yet every real request through the app's actual authenticated code path hung for about two minutes before timing out. Unauthenticated requests failed fast and cleanly; raw queries against the database directly were instant. Only the specific path that went through the running Node process was slow, which made "the config is wrong" seem like the wrong theory even though it turned out to be exactly the problem.

pm2 restart reuses cached process metadata, not the file

pm2 restart <name> (by name or id) restarts the process using PM2's own in-memory/dumped process description — including whatever environment variables were captured the last time that process was actually started from ecosystem.config.js. Editing the file afterward and running a plain restart does not re-read it. Even pm2 restart <name> --update-env did not pick up the new value in this case — the stale environment had been baked in for weeks, since the last time the process was cold-started from the file.

The actual lesson

When an ecosystem.config.js env var changes and it actually needs to take effect, don't reach for pm2 restart at all — pm2 delete <name> first, then pm2 start ecosystem.config.js (or the app's normal start command) to force a real cold start that reads the file fresh, then pm2 save. A years-old, definitely-fine-looking config file is exactly the kind of thing that stops getting double-checked — which is also exactly why this took hours to trace back to something that simple.
