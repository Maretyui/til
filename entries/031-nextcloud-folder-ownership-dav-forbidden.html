A folder's unix owner can silently break Nextcloud WebDAV moves

A folder that had briefly been used as a bind mount for another app's consume-directory kept rejecting every attempt to move files into it afterward — from the desktop sync client, the web UI, and the Android app alike. Every client reported the same generic error: 

Sabre\DAV\Exception\Forbidden: not permitted to move

No share settings, ACLs, or app permissions looked wrong anywhere in the admin UI. It genuinely looked like a Nextcloud config bug at first.

The real cause: a plain unix ownership mismatch

Every other Nextcloud-managed file and folder on disk was owned by root:root — that's simply the convention the snap install runs under, since its php-fpm process runs as root. This one folder had been created directly on disk (via a bind mount for an unrelated app, since removed) and was left owned by the actual unix login user instead, e.g. maik:maik rather than root:root.

That distinction never usually matters, because php-fpm runs as root and root can write anywhere — except here it couldn't, because the snap's AppArmor confinement profile explicitly denies the dac_override capability. Without that capability, even root is bound by normal unix permission checks and can't write into a directory it doesn't own, so every move into that one folder failed while every other folder on the same instance worked fine.

The fix

chown root:root /path/to/the/folder

One ownership change, no Nextcloud config touched at all, and moves into the folder started working immediately in every client.

The actual lesson

If a single folder in an otherwise-healthy Nextcloud instance throws a WebDAV Forbidden error that no share/ACL setting explains, check its actual unix ownership before assuming it's a Nextcloud bug — especially for any folder that was ever touched directly on disk (bind mount, SSH, rsync) rather than created through Nextcloud itself.
