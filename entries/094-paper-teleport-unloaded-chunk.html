A "/home" warp command sometimes dropped players through the floor

A warp plugin called the plain Bukkit API, player.teleport(location), to send players to a saved location. Most of the time it worked fine. Occasionally, on a warp nobody had visited in a while, the player would spawn falling through void or standing on nothing until the chunk finished generating under their feet a moment later.

Why: teleport() doesn't wait for the destination chunk to be ready

Player.teleport() is synchronous and returns as soon as the entity's position is updated - it does not block until the target chunk is loaded (or generated, if it doesn't exist yet). If the destination chunk isn't already resident in memory, the player gets moved there anyway and the chunk loads asynchronously afterward, which is exactly the gap where a player can fall or see nothing rendered. 

// naive: no guarantee the destination chunk is loaded first
player.teleport(warpLocation);

// PaperLib's async variant loads (or generates) the chunk first,
// then teleports once it's actually ready
PaperLib.teleportAsync(player, warpLocation)
    .thenAccept(success -> {
        if (!success) player.sendMessage("Teleport failed.");
    });

PaperLib's teleportAsync exists specifically to paper over this gap: it requests the chunk, waits for the load/generate to actually finish, and only then performs the teleport - all without blocking the main thread the way a manual chunk.load() call on the server thread would.

The actual lesson

Any teleport to a location that isn't guaranteed to already be loaded - a saved warp, a player-set home, a random coordinate for an event - needs an async-safe teleport helper, not the plain synchronous API. It only fails intermittently, which is exactly what made it easy to miss in testing on chunks that were already loaded from normal play.
