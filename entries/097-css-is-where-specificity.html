Swapping :where() for :is() silently changed which rule won

A shared selector list like .card p, .card ul, .card ol got collapsed into .card :is(p, ul, ol) to shorten it — purely a readability change, or so it seemed. A more specific rule elsewhere that used to lose to a later `.card ul` override suddenly started winning instead, and the override stopped applying.

Why: :is() isn't specificity-free, :where() is

Both :is() and :where() match the same elements, but they're scored completely differently. :where() always contributes zero specificity, no matter what's inside it. :is() instead takes on the specificity of its single most specific argument: 

/* :where() — contributes (0,0,0), same as no selector at all */
.card :where(p, ul, ol) { margin-bottom: 1rem; }

/* :is() — contributes the specificity of ".highlighted",
   i.e. (0,1,0), even though the plain "p"/"ul" branches match too */
.card :is(p, ul, ol.highlighted) { margin-bottom: 1rem; }

In the incident above, the original comma-separated list had each branch at plain-element specificity. Collapsing it into :is() was specificity-neutral only because every branch happened to be equally specific — the bug would have surfaced immediately if any branch had included a class or id, the way ol.highlighted does here.

The actual lesson

:is() is a shorthand for "any of these selectors", not a specificity-neutral grouping construct — reach for :where() when the goal is purely to shorten a selector list without touching the cascade, and reserve :is() for when inheriting the highest-specificity branch is actually wanted.
