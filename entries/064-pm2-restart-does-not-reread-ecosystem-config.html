A database URL update in ecosystem.config.js had zero effect after a restart

A Go API's ecosystem.config.js had its DATABASE_URL changed to point at a new host. On disk, the file was correct. But every authenticated request against the running process kept timing out after roughly two minutes, as if it were still trying to reach the old address. Unauthenticated fast-fail requests and raw queries run directly against the database both looked completely healthy, which made the failure look like an application bug rather than a stale config — only the real, fully-signed request path was affected, and that's the path nobody tests first.

Why: pm2 restart reuses PM2's own cached process metadata, not the file

Running pm2 restart <name> by name or id does not re-read ecosystem.config.js. It restarts the process using PM2's own already-cached metadata for that process — environment variables included — which was captured the last time the process was actually started from the config file. Editing the file afterward has no effect on a process that's merely restarted; the old, in-memory environment survives indefinitely across any number of restarts. Even pm2 restart <name> --update-env did not fix it in practice. 

// doesn't pick up ecosystem.config.js changes:
pm2 restart my-api

// what actually reloads the env from the file:
pm2 delete my-api
pm2 start ecosystem.config.js
pm2 save

The actual lesson

Any time an ecosystem.config.js env var changes and needs to take effect, don't reach for pm2 restart — delete the process first and start it fresh directly from the config file, then save. After doing so, it's worth verifying the change actually landed by checking the live process's real environment (e.g. /proc/<pid>/environ on Linux) rather than trusting an unauthenticated health check, since a shallow probe can look completely fine while the real authenticated path is still silently using the old value.
