Picking the same ticket category twice in a row did nothing the second time

A ticket-panel bot used a persistent StringSelectMenu for the category picker (Report / Support / Bewerbung / etc.) — one dropdown instead of a row of buttons, since a menu scales better once there are more than three or four categories. It worked the first time a user picked a category. But if a user closed their ticket and then opened a new one by selecting the exact same category from the same menu message, nothing happened — no interaction fired at all client-side, and the bot logged nothing either.

Why: Discord's client only fires on a value change

A select menu's selectMenu interaction event only fires when the chosen option differs from whatever the menu is currently rendering as selected. Since the menu component is persistent (the same message, never re-sent), the client already shows the previous pick as the active value — reselecting the identical option is treated as a no-op by the Discord client itself, and the gateway event is never even sent. This isn't something the bot's own code can special-case around, because it never receives anything to handle in that scenario. 

// looks reasonable, breaks on repeat-same-value:
new StringSelectMenuBuilder()
  .setCustomId('ticket_category')
  .addOptions(categories.map(c => ({ label: c.name, value: c.id })));

// a button per category has no "current value" to compare against,
// so every click always fires regardless of what was clicked last:
categories.map(c =>
  new ButtonBuilder().setCustomId(`ticket_create_${c.id}`).setLabel(c.name)
);

The actual lesson

Select menus are the wrong component whenever the same option might legitimately need to be chosen more than once in a row from the same persistent message — panels, repeatable actions, anything that isn't a genuine one-shot settings picker. A button-per-option layout has no stored "current selection" to compare against, so it doesn't have this failure mode at all.
