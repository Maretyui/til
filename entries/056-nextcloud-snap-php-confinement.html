occ worked a minute earlier, then the "equivalent" php command didn't

Nextcloud on this server is installed as a snap, and admin tasks normally go through its bundled nextcloud.occ command. Wanting to run one extra PHP one-liner alongside a normal occ call, calling the snap's own PHP binary directly (/snap/nextcloud/current/htdocs/occ via php) seemed like it should behave identically — same files, same install. Instead it failed immediately with a missing shared library error, something like libldap_r-2.4.so.2: cannot open shared object file, even though nextcloud.occ run right before it worked fine for the exact same task.

occ isn't just a shortcut, it's a wrapper into confinement

A snap ships its own runtime and its own copies of shared libraries, wired together with a specific LD_LIBRARY_PATH and mount namespace that only exist inside the snap's confined environment. Commands like nextcloud.occ are wrapper scripts snapd generates that enter that confinement first and then invoke the real PHP binary from inside it. Calling the same PHP binary's path directly from a normal SSH shell skips that setup entirely — the binary runs against the host's own library paths instead of the snap's, and anything the snap's PHP dynamically links against but the host doesn't have installed system-wide just fails to load.

The actual lesson

For any snap-packaged application that bundles its own runtime, reach for the snap's own command aliases (<snapname>.<command>) instead of the underlying interpreter or binary path, even when you can see the exact binary sitting right there on disk. The wrapper isn't optional convenience — it's the only supported entry point into an environment the binary actually depends on.
