git branch -a kept showing branches that were deleted on the remote weeks ago

A repo with a lot of short-lived feature branches had accumulated a long tail of remote-tracking branches (origin/some-old-branch) for branches that had long since been merged and deleted on GitHub. Running git fetch every day never cleaned any of them up, and they kept cluttering tab-completion and git branch -a.

Why: a plain fetch only ever adds refs, never removes them

git fetch updates local remote-tracking branches to match what the remote currently has, but by design it never deletes a remote-tracking ref just because the corresponding branch disappeared upstream - that cleanup is opt-in via --prune (or the persistent fetch.prune = true config). 

# stop guessing which origin/* refs are actually still real
git fetch --prune

# make it the default for every fetch in this repo
git config fetch.prune true

Even with pruning on, this only ever touches remote-tracking branches like origin/some-old-branch - it does not touch local branches. A local branch that was tracking a now-deleted remote branch is left alone entirely, including its upstream link, which just starts pointing at nothing. git branch --merged (or git branch -vv to spot the "gone" markers) is still a separate, manual step for cleaning those up.

The actual lesson

Fetching is additive by default; pruning stale remote-tracking refs is a separate opt-in, and even then it's scoped to origin/* refs, not the local branches sitting next to them. Two different kinds of leftovers, two different cleanup steps.
