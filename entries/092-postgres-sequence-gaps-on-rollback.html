A SERIAL id column had gaps even though nothing was ever deleted

A table with a plain id SERIAL PRIMARY KEY column had visible gaps in its ids - row 41 followed by row 44, with no delete in sight. The app had a validation step inside the same transaction as the insert, which sometimes rolled the insert back. It looked like those rolled-back inserts should never have consumed an id at all.

Why: nextval() isn't transactional

SERIAL (and GENERATED ... AS IDENTITY) is backed by a separate sequence object, and nextval() is deliberately excluded from normal MVCC/transaction rollback - it's documented as non-transactional specifically so concurrent transactions never have to block on each other just to get a unique number. 

BEGIN;
INSERT INTO widgets (name) VALUES ('test'); -- consumes id 44 from the sequence
ROLLBACK;                                   -- the insert is undone, id 44 is not returned

INSERT INTO widgets (name) VALUES ('real one'); -- gets id 45, not 44

Once nextval() hands out a number, that number is gone for good, whether the transaction that requested it commits, rolls back, or the whole connection crashes mid-transaction. The sequence only ever moves forward.

The actual lesson

A gap in a sequence-backed id column is not evidence of a deleted row or a bug - it's the normal, documented cost of sequences being fast and non-blocking under concurrency. If a column genuinely needs to be gap-free (an invoice number, say), a sequence is the wrong tool for it; that needs an explicit locking scheme instead.
