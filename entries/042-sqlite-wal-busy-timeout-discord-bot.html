A Discord ticket bot occasionally threw SQLITE_BUSY under load

A small discord.js ticket bot backed by SQLite worked fine in testing, but under real production traffic — several staff members clicking claim/close/priority buttons within the same second — an occasional handler crashed with SQLITE_BUSY: database is locked. WAL mode was already enabled, which is supposed to be the fix for concurrent readers/writers not blocking each other.

WAL fixes readers-vs-writer, not writer-vs-writer

Write-ahead logging lets readers keep reading a stable snapshot while a writer appends to the WAL file, so reads and writes no longer block each other the way rollback-journal mode does. It does not mean two writers can commit at literally the same instant — SQLite still serializes writes with a single reserved lock, and by default a second writer that can't immediately get it fails instantly with SQLITE_BUSY instead of waiting. 

-- enabled, but not sufficient on its own under concurrent writes:
PRAGMA journal_mode = WAL;

-- the missing piece: make a blocked writer retry for up to N ms
-- instead of failing immediately
PRAGMA busy_timeout = 5000;

The actual lesson

busy_timeout (or the equivalent option in whatever SQLite driver/library is in use — better-sqlite3's pragma('busy_timeout = 5000') in this case) turns a near-instant lock collision from a hard failure into a short, invisible retry-and-wait. WAL mode alone only solves half of the concurrency problem; a real busy timeout is what actually closes the gap for the two-writers-at-once case.
