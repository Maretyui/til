A command block chain that worked in testing did nothing for half the playerbase

A minigame lobby used a scoreboard objective to gate a command chain — only players past a certain score should get teleported to the arena. It worked perfectly for anyone who'd played a round before. Brand new players, whose score for that objective had never been set at all, just stood at the lobby spawn with no error, no message, and nothing in the command block output to say why the condition failed.

Why: "no score" and "score of 0" are different things /execute if score can't confuse, but a player can

/execute if score <target> <objective> matches <range> only evaluates true if the target actually has an entry on that objective's scoreboard. A player who was never /scoreboard players set or add'd onto it has no score at all — not zero, genuinely absent — and the condition silently resolves to false for any range, including matches 0..: 

# looks like it should pass for a brand new player with "no progress yet"
execute if score @s minigame_wins matches 0.. run teleport @s arena

# but a player who was never added to the objective has no score row,
# not a score of 0 — this condition is false for them, every time

The lobby's own join script only called /scoreboard players add @s minigame_wins 0 the first time someone actually finished a round, so anyone who hadn't yet had no row to match against.

The actual lesson

Any objective a command chain gates logic on needs every player explicitly initialized onto it — typically with scoreboard players add @s <objective> 0 on first join — before the first /execute if score check against them ever runs. There's no "treat missing as zero" fallback in the command syntax itself; an absent score and a present zero score are indistinguishable in-game until you check the objective's tracker and notice the player's name just isn't listed at all.
