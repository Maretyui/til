A deploy script's --exclude looked safe, until a rename happened

A deploy recipe synced a build folder to a server with rsync -avz --delete --exclude='uploads/' . user@host:/srv/app/, the standard pattern for keeping a server-only uploads directory untouched while still mirroring everything else exactly. It had worked for months. Then the uploads directory got renamed locally (a one-off cleanup, unrelated to the deploy itself) without updating the exclude pattern to match — and the next deploy quietly deleted every file the server had under the old directory name.

Why: --exclude only protects a path that exists identically on both sides

--delete works by diffing what the destination has against what the source has (after excludes are applied) and removing anything on the destination that isn't in that filtered source list. An --exclude pattern doesn't mean "never touch this path on the destination" — it means "don't consider this path when comparing." If the source no longer has a directory under that name at all (renamed, deleted, or just typo'd in the exclude flag), rsync has nothing to exclude by that name anymore, and the destination's matching directory looks like plain drift to be deleted, not protected data. 

# source renamed uploads/ -> media/ locally, but the deploy
# script still says:
rsync -avz --delete --exclude='uploads/' . user@example.com:/srv/app/
# rsync now sees no local uploads/ to exclude, and no local
# uploads/ to keep either -> the remote uploads/ just looks deleted

# --dry-run always shows exactly what would be removed first:
rsync -avzn --delete --exclude='uploads/' . user@example.com:/srv/app/
# a real uploads/*** line in that output means the exclude
# pattern no longer matches anything real

The actual lesson

An exclude pattern is coupled to the source tree's current shape, not a standing promise about the destination. Any rename, path restructuring, or deploy-script refactor near an excluded server-only directory needs the exclude flag checked and updated in the same change — and a --dry-run pass before any --delete sync is cheap insurance against exactly this.
