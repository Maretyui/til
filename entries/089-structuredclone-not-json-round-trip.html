Swapping in structuredClone() as a "safer JSON round-trip" broke a config object

A deep-clone helper used the classic JSON.parse(JSON.stringify(obj)) trick, which silently drops anything JSON can't represent. Swapping it for structuredClone() looked like a pure improvement — same job, fewer footguns — until it started throwing on an object that the JSON version had cloned without complaint.

Why: they fail in opposite directions

JSON.stringify() quietly drops values it can't encode — functions and undefined properties vanish, Date becomes a plain string, Map/Set become {}. It never throws for these, it just loses data. structuredClone() goes the other way: it uses the structured clone algorithm, which knows about Date, Map, Set, RegExp, typed arrays and cyclic references and clones all of them correctly — but if the object contains a function, a DOM node, or an Error subclass with extra properties, it throws a DataCloneError instead of silently dropping it. 

const obj = { when: new Date(), onDone: () => {} };

JSON.parse(JSON.stringify(obj));
// => { when: "2026-09-26T10:00:00.000Z" } — Date stringified, function gone, no error

structuredClone(obj);
// => Uncaught DOMException: could not be cloned. (onDone is a function)

The actual lesson

Neither one is strictly "safer" — they just fail differently. structuredClone() is the right choice when the data is genuinely structured-cloneable (dates, maps, sets, nested plain objects/arrays) and you'd rather get a loud error than silent data loss. If the object might carry incidental functions or other non-cloneable values that are fine to lose, the JSON round-trip's silent-drop behavior is actually the more forgiving one — swapping between them isn't a like-for-like substitution, it changes which failure mode you get.
