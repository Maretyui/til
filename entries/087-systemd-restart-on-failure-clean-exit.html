A worker process kept dying and systemd just... let it stay dead

A small background worker unit had Restart=on-failure set, which sounds like it should cover "the process died unexpectedly." A bug in the worker's shutdown path made it call process.exit(0) on an unhandled condition instead of throwing — and systemd left it stopped instead of restarting it, with nothing but a quiet gap in the logs to show for it.

Why: "on-failure" means a specific list of exit conditions, not "the process is gone"

Restart=on-failure only restarts the unit if it exits with a non-zero code, is terminated by a signal, hits a timeout, or fails a watchdog check. An exit code of 0 is, by definition, a "clean" exit — even if nothing about the situation that caused it was actually clean. systemd has no way to know the difference between a deliberate shutdown and a bug that happens to call exit(0). 

[Service]
ExecStart=/usr/bin/node worker.js
# Restarts on crashes/signals/timeouts, but NOT on a plain exit code 0:
Restart=on-failure

# What actually covers "the process is gone, for any reason":
Restart=always

The actual lesson

For anything that's supposed to keep running indefinitely, Restart=always is almost always the safer default — on-failure only makes sense for units that have a legitimate, intentional "done, exit 0" state. Also worth checking: SuccessExitStatus= can widen what counts as "successful" if a unit's clean-shutdown path uses a nonzero code for some reason, but that doesn't help the reverse case above.
