Docker's embedded DNS can look IPv6-only while TCP-by-hostname still works fine

Debugging a Minecraft proxy's connection to a backend server (containers on the same Docker bridge network, addressed by container name instead of a hardcoded IP — the fix for IPs reshuffling across restarts), a sanity check with getent hosts <container-name> from inside the proxy container returned only an IPv6 address. That looked alarming at first: the backend's own listener was IPv4-only, so an IPv6-only DNS answer looks like it should fail outright.

Dual-stack subnet, but the connection still lands

The bridge network in question was configured dual-stack, and Docker's embedded DNS (the resolver at 127.0.0.11 inside every container on a user-defined network) will return whichever address family it has for a name — on this subnet, that was the IPv6 record. But the actual outbound connection made by the application (a plain TCP socket connect using the hostname, not a raw getent lookup) resolved and connected correctly anyway, verified with a direct curl from inside the container. 

# looks IPv6-only, seems wrong for an IPv4-only backend
getent hosts backend-container-name
# fd00:1234::abcd  backend-container-name

# but this just works
curl -v telnet://backend-container-name:25565

The actual lesson

getent hosts only shows what one specific resolver call returned, not what the application's own connect path will actually do — Docker's embedded DNS and the container network stack can still route a hostname-based TCP connection correctly even when a manual lookup looks IPv4-incomplete. Don't treat getent/dig output as the final word on whether hostname-based container-to-container networking will work; test the real connection path (a raw curl or the application itself) before concluding DNS is broken.
