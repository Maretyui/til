wp-cli said the URL was updated, but nothing changed

A local dockerized WordPress instance kept resolving to the wrong base URL — login redirects, asset paths, everything pointed at a stale host. wp option update siteurl https://correct-host ran clean and even wp option get siteurl echoed the new value back. Every page load still used the old one.

Why: a defined constant wins over the database option, but the CLI doesn't tell you that

WordPress core checks for the WP_SITEURL/WP_HOME PHP constants before it ever reads the siteurl/home rows in wp_options. If either constant is defined anywhere in the load path — most commonly a define() baked into wp-config.php, or in this case an env var injected as extra config by the official Docker image — it wins unconditionally, and wp option get is misleading here: it reads back the *effective* value (the constant), which makes a successful-looking option update look like it took effect when it never touched the real source of truth. 

# docker-compose.yml — the actual override, easy to miss
environment:
  WORDPRESS_CONFIG_EXTRA: |
    define('WP_SITEURL', 'https://old-host');
    define('WP_HOME', 'https://old-host');

The actual lesson

If a WordPress site's URL seems "stuck" despite a clean wp option update, grep the actual wp-config.php (and, for Docker installs, the compose file's env block) for WP_SITEURL/WP_HOME constants before spending more time on the database. Fixing the constant — then recreating the container so the new env value actually loads — is the real fix; editing the option again just repeats the same no-op.
