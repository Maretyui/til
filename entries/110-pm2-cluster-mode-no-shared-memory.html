Switching a Node app to PM2 cluster mode broke a simple in-memory rate limiter

A small Express API kept a Map in module scope to count requests per IP for basic rate limiting. It worked fine under pm2 start app.js. Flipping on cluster mode with pm2 start app.js -i 4 to use all CPU cores made the limiter effectively stop working: the same IP could blow past the configured limit, and logs showed request counts that never climbed past small, inconsistent numbers no matter how fast the client hammered the endpoint.

Why: -i 4 is four separate processes, not four threads

PM2's cluster mode is Node's built-in cluster module under the hood — each instance is its own OS process with its own heap, forked from the master and load-balanced round-robin by the master's socket handoff. A module-scope Map, counter, or cache only lives inside the one process that created it. With 4 instances, a client's requests get spread across up to 4 completely separate copies of that Map, so the "same" rate limiter sees roughly a quarter of the real traffic in each process and never reaches the configured threshold. 

// module scope — looks shared, isn't, once cluster mode is on
const hits = new Map();

app.use((req, res, next) => {
  const count = (hits.get(req.ip) ?? 0) + 1;
  hits.set(req.ip, count);
  if (count > 100) return res.sendStatus(429);
  next();
});
// each of the 4 forked processes has its OWN hits Map

The same gap shows up for anything else kept in process memory across cluster instances: an in-memory session store, a feature-flag cache refreshed on a timer, a websocket connection registry, an in-flight-request dedupe table. Each works perfectly in single-instance mode and silently fragments the moment -i goes above 1, with no error — just state that looks inconsistent depending on which instance happened to handle a given request.

The actual lesson

Anything that needs to be consistent across cluster instances has to live outside any single process — Redis for rate limiters and session stores, a database row for feature flags, a pub/sub channel for things that need to fan out to every instance. Before relying on cluster mode (or any multi-process deployment) for throughput, audit module-scope state for exactly this: if it would break with two independent copies of the process running side by side, it needs to move out of memory first.
