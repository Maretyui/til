Every player's inventory and advancements looked wiped after a config change nobody thought was risky

A test server got flipped from online-mode=false back to online-mode=true in server.properties once it was ready to open up to real accounts again. On the next join, every returning player loaded in with a fresh inventory, no advancements, and starting-area spawn coordinates — as if their playerdata had been deleted, even though the world/playerdata/ folder was untouched.

Why: the UUID a player is saved under depends on where it came from

Minecraft stores per-player data in world/playerdata/<uuid>.dat, keyed by UUID rather than username. In online mode, that UUID is the player's real Mojang account UUID, looked up from Mojang's servers on join. In offline mode, there's no account to look up, so the server derives a UUID itself — a version-3 (name-based) UUID hashed from the literal string "OfflinePlayer:" + username: 

// Conceptually, what the server does in offline mode:
UUID offlineUUID = UUID.nameUUIDFromBytes(
  ("OfflinePlayer:" + username).getBytes(StandardCharsets.UTF_8)
);

Flipping online-mode swaps which of those two UUIDs a given username resolves to. The old offline-mode .dat file is still sitting in playerdata/ on disk, fully intact — it's just filed under a UUID the server no longer looks up for that username, so a brand-new file gets created instead.

The actual lesson

Nothing was lost, but nothing migrates automatically either. Going from offline to online mode (or back) on a server with real player progress needs the old <offline-uuid>.dat renamed to the new UUID before players rejoin — or a one-time migration tool that resolves each known username to its online-mode UUID and renames the file (and the matching entries in whitelist.json, ops.json, and usercache.json, which are all also keyed by UUID) accordingly. Treat an online-mode toggle on an already-populated server as a data migration, not a one-line config edit.
