systemd-resolved's stub listener can block a port 53 publish with no visible socket

Standing up a local DNS resolver in Docker (bridge mode, publishing 53:53/udp and 53:53/tcp) failed with Docker's own "address already in use" error. The obvious next step — find whatever's holding port 53 and stop it — went nowhere: ss -tulpn, lsof -i :53, and a scan of iptables NAT rules all came up empty. Even a full systemctl restart docker didn't clear it.

The listener that doesn't show up where you'd look

systemd-resolved ships a "stub listener" that answers DNS queries on 127.0.0.53:53 (and sometimes 127.0.0.54) for local processes that read /etc/resolv.conf. Because it's bound to a loopback alias rather than 0.0.0.0, generic port-scanning commands run without matching the exact loopback address don't surface it as an obvious conflict — but Docker's bridge-mode port publish still collides with it at the kernel level when the container tries to bind all interfaces on 53. 

# confirms the stub listener's actual bind address
ss -tulpn | grep ':53'
# tcp   LISTEN 0  4096  127.0.0.53:53  0.0.0.0:*  users:(("systemd-resolve",...))

# the fix: disable the stub listener entirely, then restart resolved
# /etc/systemd/resolved.conf.d/no-stub.conf
[Resolve]
DNSStubListener=no

The actual lesson

After systemctl restart systemd-resolved, Docker's port 53 publish bound cleanly. One side effect worth knowing in advance: disabling the stub listener can leave /etc/resolv.conf pointing at a now-dead loopback address, breaking the host's own DNS resolution until whatever manages that file (Tailscale's MagicDNS, in this case) regenerates it — a quick systemctl restart tailscaled fixed that part. If a container port bind fails with no matching socket in the usual tools, check for a loopback-bound stub listener before assuming the conflict report is wrong.
