A cache payload had fewer keys after a round trip than before it

An object built from a form had a few optional fields set to undefined when left blank, rather than omitted entirely. It got JSON.stringify'd into a cache entry, then read back out with JSON.parse — and code that checked 'discount' in parsed to decide whether a field had ever been touched started getting the wrong answer. The key wasn't missing before the round trip. It was missing after.

Why: undefined isn't valid JSON, so stringify just skips it

JSON has no undefined value, so JSON.stringify doesn't error on it and doesn't coerce it to null either — for a plain object property, it drops the key outright: 

JSON.stringify({ a: 1, b: undefined, c: 3 });
// '{"a":1,"c":3}'  — "b" is just gone

JSON.stringify([1, undefined, 3]);
// '[1,null,3]'  — same value, kept as null to preserve array length

The asymmetry is the trap: the exact same undefined value is silently deleted inside an object but silently converted to null inside an array, because an array's indices have to stay contiguous and a hole would shift every later index. Nested objects and toJSON() methods go through the same rule, so a deeply nested optional field disappears the same way.

The actual lesson

Don't rely on 'key' in obj or Object.keys(obj).length surviving a JSON.stringify/JSON.parse round trip if any property might be undefined — either normalize optional fields to null before serializing, or check with obj.key === undefined after parsing instead of a presence check, since both "never set" and "explicitly cleared" now look identical anyway.
