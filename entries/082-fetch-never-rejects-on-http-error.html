A contact form silently "succeeded" while the API had returned a 500

A small contact-form endpoint failed on the server (a bad env var caused the mail step to throw), returning a 500 with a JSON error body. The frontend's try/catch around the fetch() call never caught anything, though — the success toast fired every time, even for requests that had visibly failed server-side.

Why: a non-2xx status code is not a fetch failure

fetch() only rejects its promise for genuine network- level failures — DNS not resolving, the connection being refused, a CORS block, the request being aborted. Once a response actually comes back from the server, fetch() resolves successfully no matter what status code is attached to it. A 404 or a 500 is, as far as the promise is concerned, just as much a "success" as a 200. 

const res = await fetch('/api/contact', { method: 'POST', body });
// res.ok is false and res.status is 500, but nothing threw —
// this line runs regardless of whether the request "succeeded":
showSuccessToast();

// The check that was actually missing:
if (!res.ok) {
  throw new Error(`Request failed: ${res.status}`);
}

This is different from most other HTTP client libraries by design — older tools like jQuery's $.ajax or Axios treat a non-2xx status as a rejected promise out of the box. Plain fetch() deliberately does not, on the reasoning that a 4xx/5xx response is still a "successful" HTTP exchange at the transport level.

The actual lesson

Every fetch() call that cares about failure needs an explicit if (!res.ok) check (or reading res.status) before treating the response as good — the try/catch around it only ever catches the network layer, never the application layer.
