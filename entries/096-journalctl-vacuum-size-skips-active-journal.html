A disk-space alert didn't budge after running journalctl --vacuum-size

A host was flagged for low disk space, and /var/log/journal looked like the obvious culprit. Running journalctl --vacuum-size=200M reported success and deleted a handful of old files, but df barely moved - a multi-gigabyte journal directory stayed multi-gigabyte.

Why: vacuum only removes archived files, not the active one

systemd-journald keeps logs in rotated segments. Only sealed, archived segments (named like system@<id>-...-...journal) are eligible for --vacuum-size/--vacuum-time/--vacuum-files to delete. The single system.journal file currently being written to is exempt no matter how large it's grown - vacuuming can't touch a file the daemon still has open for writes. 

# shows how big the live file actually is
journalctl --disk-usage

# does nothing for system.journal itself, only archived segments
journalctl --vacuum-size=200M

# force a rotation first, which seals the active file into an
# archived one - only then does vacuum have something to remove
journalctl --rotate
journalctl --vacuum-size=200M

In this case the active file alone had grown past the configured SystemMaxUse because a noisy service was logging in a tight loop and no rotation had happened recently - rotating first, then vacuuming, is what actually freed the space.

The actual lesson

"Vacuum" and "rotate" are two separate, ordered operations, not one command that does both. If disk usage doesn't drop after a vacuum, check whether the bulk of it is sitting in the still-open active journal - a manual --rotate is the missing step, not a bigger --vacuum-size number.
