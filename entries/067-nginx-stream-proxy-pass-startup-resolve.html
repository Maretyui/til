One offline backend killed every site on the reverse proxy, not just its own

A TCP stream (a raw port forward, separate from the normal HTTP(S) proxy hosts) pointed at a backend by hostname. That backend host happened to be off for an unrelated reason, so its hostname briefly stopped resolving. Instead of just that one stream failing, the whole reverse proxy's nginx process refused to start at all — meaning every other proxied domain on the same box went down with it, admin UI included.

Why: a bare hostname in proxy_pass is resolved once, at config load

A plain proxy_pass http://backend:port; (or its stream-block equivalent) asks nginx to resolve that name during config parsing, before the server even starts accepting connections. If the name doesn't resolve at that exact moment, nginx logs host not found in upstream and exits — it does not fall back to trying again later, and it does not isolate the failure to just that one server block. 

server {
  listen 25565;
  # resolved ONCE, when nginx starts/reloads:
  proxy_pass backend.internal:25565;
}

server {
  listen 25565;
  # resolved on EVERY connection, using the given DNS resolver:
  resolver 100.100.100.100 valid=10s;
  set $upstream backend.internal;
  proxy_pass $upstream:25565;
}

The actual lesson

Any dynamic hostname in a proxy_pass — one that might legitimately be offline sometimes — should go through a resolver directive plus an nginx variable instead of being written literally. The variable form defers resolution to request time using the given DNS resolver, so a temporarily-dead backend just fails that one connection instead of preventing the entire process from starting. Worth checking any proxy config template that generates these blocks automatically, since the bug is invisible until the one backend it points at happens to be down at exactly the moment the proxy itself restarts.
