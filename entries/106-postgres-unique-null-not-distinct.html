A nullable "external id" column kept duplicating rows past a UNIQUE constraint

A table had an optional external_ref column with a plain UNIQUE constraint on it, meant to stop the same external record from ever being linked twice. Rows that hadn't been linked yet left the column NULL — and dozens of those unlinked rows inserted just fine side by side, which looked like the constraint wasn't being enforced at all.

Why: SQL treats NULL as not equal to itself, and UNIQUE follows that rule

A UNIQUE constraint rejects a new row only if an existing row compares as equal to it on the constrained columns, and in SQL's three-valued logic NULL = NULL doesn't evaluate to true — it evaluates to unknown. So every NULL is treated as distinct from every other NULL, and the constraint has nothing to reject. Postgres isn't unusual here; this is the SQL standard's behavior, and MySQL/SQLite follow it too. 

create table links (
  id serial primary key,
  external_ref text unique
);

insert into links (external_ref) values (null);
insert into links (external_ref) values (null); -- succeeds, no conflict
insert into links (external_ref) values ('abc-123');
insert into links (external_ref) values ('abc-123'); -- this one fails

Postgres 15 added an explicit way to opt out of this if the goal really is "at most one NULL too": UNIQUE NULLS NOT DISTINCT on the column or constraint definition makes all NULLs collide with each other instead of being treated as unique snowflakes. 

-- Postgres 15+: now a second NULL insert also fails
alter table links
  drop constraint links_external_ref_key,
  add constraint links_external_ref_key
    unique nulls not distinct (external_ref);

The actual lesson

A bare UNIQUE on a nullable column only dedupes the non-NULL values — if "unlinked"/"not set yet" rows need to be capped at one too, that has to be either NULLS NOT DISTINCT (15+) or a partial unique index with a WHERE clause carving out a separate rule for the NULL case, not the plain constraint alone.
