A typo'd config field passed satisfies without a single complaint

A small config object was being validated against an interface with satisfies instead of a type annotation, specifically to keep the narrower literal type for later use. A field had been misspelled — verbse instead of verbose — and TypeScript never flagged it, even though the exact same typo on a plain object-literal annotation gets caught immediately. 

interface Config {
  mode: "dev" | "prod";
  verbose: boolean;
}

const raw = { mode: "dev", verbse: true };
const config = raw satisfies Config; // no error, "verbse" silently ignored

Why: excess-property checking only applies to a fresh literal

TypeScript's excess-property check — the thing that normally rejects an object literal with a field the target type doesn't know about — only fires when the literal is written directly at the checked position. The moment it's assigned to a variable first, it stops being a "fresh" literal as far as the checker is concerned, and only ordinary structural compatibility applies: having every required property is enough, extra properties are fine. satisfies doesn't change that rule, it just runs the same check at a different point: 

// caught — the literal is fresh right here
const config2 = { mode: "dev", verbse: true } satisfies Config;
//                              ^^^^^^ Error: Object literal may only
//                              specify known properties, and 'verbse'
//                              does not exist in type 'Config'.

The actual lesson

satisfies is only as strict as a direct literal check — routing the object through an intermediate const, a spread, or a factory function before the satisfies clause quietly turns off excess-property checking, typos and all. If the value doesn't originate as a literal at the checked expression, satisfies is only verifying "has the right shape," not "has exactly the right shape."
