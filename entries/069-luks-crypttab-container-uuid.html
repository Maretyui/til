An encrypted drive that opened fine by hand, but silently stayed locked on boot

After putting LUKS2 full-disk encryption on an external backup drive, manually running cryptsetup luksOpen and mounting it worked every time. But a fresh reboot left the mapped device missing entirely — no error, the automount unit just had nothing to attach to, as if the entry didn't exist.

Why: two different UUIDs live on the same physical disk

A LUKS-encrypted disk actually has two UUIDs: one for the LUKS container itself (what blkid reports for the raw partition, e.g. /dev/sda1), and a completely separate one for the filesystem that lives inside the decrypted container (what shows up once it's mapped to /dev/mapper/<name>). It's easy to grab the wrong one from a quick lsblk -f glance, since both look like valid UUIDs sitting on the same device.

/etc/crypttab needs the outer LUKS container's UUID — the one cryptsetup itself unlocks. Point it at the inner filesystem UUID instead, and systemd-cryptsetup fails to find anything matching that identifier at boot, so the mapped device is just never created. No error surfaces because, as far as boot is concerned, there was nothing to open. 

# get both, don't assume which one you're looking at:
lsblk -f
#   /dev/sda1        crypto_LUKS     <- this one, for crypttab
#   /dev/mapper/name  ext4          <- not this one

# /etc/crypttab
backup UUID=<container-uuid> /etc/luks/backup.key luks,nofail

# verify the mapped device actually exists after a real reboot,
# don't just trust a manual `cryptsetup open` test:
findmnt /mnt/backup   # should show /dev/mapper/backup as the source

The actual lesson

When a config file wants a UUID and the same physical device legitimately has more than one, don't grab the first UUID a listing tool shows — confirm which layer it belongs to. A manual unlock test isn't a substitute for a real reboot test either: it exercises the crypto layer but not the automount path that only runs during actual boot.
