Deleting a parent row left orphaned child rows, despite a declared foreign key

A small Discord bot stored data in SQLite with a schema that declared FOREIGN KEY (guild_id) REFERENCES guilds(id) ON DELETE CASCADE. A one-off cleanup script opened its own connection, ran PRAGMA foreign_keys = ON; first, and deleting a guild row there correctly cascaded. The bot's own long-running process never cascaded anything — deleting the same guild through it left every child row behind, silently orphaned.

Why: it's a per-connection setting, and it defaults to off

SQLite enforces foreign keys only when PRAGMA foreign_keys = ON has been run on that specific connection, and that setting does not persist in the database file — it resets to SQLite's default of OFF every time a new connection opens. A migration or seed script that enables it once is only enabling it for its own connection's lifetime; every other connection (the bot's main process, a worker, a REPL opened to poke at the data) starts back at off unless it issues the same pragma itself. 

-- Cleanup script's connection: cascades deletes correctly
PRAGMA foreign_keys = ON;
DELETE FROM guilds WHERE id = 123;

-- A completely separate connection to the same .db file, e.g. the
-- bot's own long-running process - starts fresh, defaults to OFF:
DELETE FROM guilds WHERE id = 456;
-- rows in child tables referencing guild 456 are left behind,
-- and no constraint violation is ever raised on insert either

Connection pools make this worse than a single bad script: even if application startup code runs the pragma once against "the database," most SQLite client libraries hand out a fresh connection (or a pooled one that was opened before that startup code ran) per request or per worker, and each of those needs the pragma re-applied individually — usually from a per-connection "on open" hook, not a one-time call during boot.

The actual lesson

Treat PRAGMA foreign_keys = ON the same way as any other per-connection session setting (like PRAGMA journal_mode's cousin settings that aren't persisted) — wire it into whatever hook fires on every new connection a library opens, not into a migration or startup script that only touches one connection. Declaring the foreign key in the schema is necessary but not sufficient; without the pragma actually set on the connection doing the writing, SQLite accepts the schema and then quietly ignores it.
