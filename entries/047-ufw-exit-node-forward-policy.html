Locking down a box with ufw also silently killed its one real job

A small VPS was doing double duty as a Tailscale exit node — mesh devices route their internet-bound traffic through it so they get its public IP as their egress address. It had no firewall at all, which was overdue for fixing given the SSH brute-force noise it was taking on its public IP. Enabling ufw with a sane default-deny posture seemed like the obvious move.

Why: ufw's default FORWARD policy quietly breaks exit-node routing

An exit node's whole function is forwarding — packets come in from one interface (the Tailscale mesh) and go back out another (the public interface), rather than being addressed to the box itself. ufw's out-of-the-box default sets DEFAULT_FORWARD_POLICY to DROP, since most hosts should never route third-party traffic. On an exit node, that default drops every packet the whole feature depends on — Tailscale's own ts-forward chain still runs (it's jumped to before ufw's own forward chains), but ufw's policy silently discards what comes out the other side. 

# /etc/default/ufw
DEFAULT_FORWARD_POLICY="ACCEPT"

# and allow routing in general
ufw default allow routed

The actual lesson

Any host acting as a router/relay (Tailscale exit node, VPN gateway, NAT box) needs its firewall's forward policy treated as a separate question from its input policy — a correct, restrictive ufw default deny incoming can still coexist with allow routed/FORWARD ACCEPT, since inbound traffic addressed to the host itself and traffic merely passing through it are governed by entirely different iptables chains. Test the actual forwarded path (route a real device through the exit node and check its egress IP) after any firewall change on a box like this, not just SSH reachability — SSH working fine gives no signal at all about whether forwarding still does.
