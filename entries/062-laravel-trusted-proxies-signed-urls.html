File uploads through signed URLs kept failing with a bare 401, no explanation

A Laravel-based admin panel sits behind a reverse proxy that terminates HTTPS and forwards plain HTTP internally — completely standard. Most of the app worked fine, but one feature relying on Laravel's signed URLs (an upload widget verifying a time-limited signed request) failed every time with a silent 401 and no useful error in the logs. A settings page in the app even had a "trusted proxies" field, already filled in with the proxy's IP, which made the failure look impossible at first.

Why: the settings field existed but was never actually connected to the framework

The app had a config file and a UI field for trusted proxies, but the actual framework-level call that makes Laravel honor forwarded-request headers was simply missing from the app's bootstrap code. Without it, Laravel builds signed URLs and later validates them using the connection it directly sees — the plain HTTP request from the proxy — rather than the real HTTPS scheme and host the browser used. A signature computed against https://host/... doesn't match validation performed against http://host/..., so it fails silently as an invalid signature, which surfaces as a generic 401 with nothing pointing at the actual mismatch. 

// looked configured (config file + UI field), but nothing
// in the app ever actually called this:
$middleware->trustProxies(
    at: array_filter(explode(',', (string) env('TRUSTED_PROXIES', '')))
);

The actual lesson

A framework config value or admin-UI field existing is not proof it's wired up — some settings are just data until a specific framework call actually reads and applies them. When anything relying on the "real" scheme/host/IP behind a reverse proxy misbehaves (signed URLs, redirects, rate limiting by IP), verify the trusted-proxy middleware is genuinely registered in the app's bootstrap, not just present as a config value that looks correct.
