A booking saved as "the 30th" displayed as "the 29th" for some users

A date picker handed back a plain "2026-10-30" string, which got stored as-is and later turned into a Date to format for display. For anyone west of UTC — including a server running in a different timezone than the browser that first saved it — the date on screen was one day earlier than what was picked.

Why: a date-only string and a full timestamp parse completely differently

Per spec, new Date(string) treats a bare YYYY-MM-DD string as UTC midnight, but a string with a time component attached is parsed in the local timezone. Adding a time doesn't just add precision, it switches which clock the parser uses: 

new Date("2026-10-30");            // UTC midnight on the 30th
new Date("2026-10-30T00:00:00");   // local midnight on the 30th

// in a UTC-5 timezone, formatting the first one locally
// rolls it back to 7pm on the 29th
new Date("2026-10-30").toString();
// "Thu Oct 29 2026 19:00:00 GMT-0500"

The actual lesson

A value that's conceptually a calendar date — a birthday, a booking day, a deadline with no time of day — shouldn't round-trip through Date parsing at all if it can be avoided; split it into year/month/day fields, or at minimum always attach a time component ("T00:00:00") before parsing so the local-timezone path is used instead of the UTC one. The bug doesn't show up for whoever sits in UTC+0 while testing, which is exactly how it reached production unnoticed.
