Nginx Proxy Manager deletes a proxy host's config if regeneration fails

After editing a proxy host in Nginx Proxy Manager's UI — nothing exotic, just adding a custom location — the site it fronted started throwing ERR_SSL_UNRECOGNIZED_NAME_ALERT. The proxy host record in NPM's own UI still looked completely correct: right domain, right SSL certificate, right forward target.

The cause

NPM keeps each proxy host as a generated nginx config file under /data/nginx/proxy_host/<id>.conf inside its container. Its internal configure() flow does roughly: 

1. delete the existing <id>.conf
2. render a new one from the current database record
3. run `nginx -t` against it
4. if the test fails, log the error to an internal `meta` field
   (never surfaced in the UI) — and leave the file deleted

Step 4 is the trap: on a template-generation edge case, the new config fails nginx's syntax test, and NPM does not fall back to restoring the previous, working file. It just leaves the host with no config on disk at all, while the database record — and the admin UI reading from it — still shows a perfectly valid configuration.

The fix

Since the database record is intact, the working config can be hand-reconstructed from it and dropped straight into the container, bypassing NPM's own broken regeneration path: 

# read the stored proxy host settings
sqlite3 /opt/npm/data/database.sqlite \
  "select * from proxy_host where id = 28;"

# write proxy_host/28.conf by hand based on that record, then:
docker cp 28.conf npm-app-1:/data/nginx/proxy_host/28.conf
docker exec npm-app-1 nginx -t
docker exec npm-app-1 nginx -s reload

Worth checking for this specific failure mode any time a proxy host edit "saves fine" in NPM's UI but the site immediately starts failing TLS — the UI honestly has no way to tell you the config file behind it just vanished.
